# アキバ絶対領域 お給仕カレンダー

アキバ絶対領域の公開情報を、昼・夜に分けた月間カレンダーで閲覧するための静的サイトです。メイド・日付で絞り込めます。

公開サイト: <https://agurakakenai.github.io/akibazettai-schedule-calendar/>

## ローカルプレビュー

依存パッケージやビルドは不要です。[`preview.cmd`](preview.cmd) をダブルクリックし、ブラウザーで <http://localhost:4173> を開いてください。

コマンドで起動する場合は、リポジトリのルートで次を実行します。

```powershell
py -m http.server 4173 --bind 127.0.0.1
```

`--bind 127.0.0.1` を付けているため、同じネットワークの他の端末からは見えません。

> Windows で `python` がマイクロソフトストアのスタブになっていることがあります。その場合は `py` を使ってください。

データ検証:

```powershell
node tests/validate-schedule.js
node tests/date-defaults.js
node tests/range-rendering.js
node tests/validate-insights.js
node tests/store-outlook.js
node tests/headless-render.js
```

`validate-insights.js` は [`data/store-insights.js`](data/store-insights.js) の形（店舗ID・確率の範囲・`roster` との一致など）を、`store-outlook.js` は `app.js` の「実績 / 翌日見込み / 同日の実績 / 曜日傾向」を選ぶロジックを検証します。`headless-render.js` は最小の DOM シムでカレンダーを実際に描画し、描画時のランタイムエラーやバッジ・チップの中身を確認します（依存パッケージは不要です）。**3つの表示モードすべてを描き、「予測」と「この人はどこ」が同じ人・同じ日に同じ店を出すことも突き合わせます。**

## 店舗の見込み表示

**表示モードを3つ用意しています。**左の「表示モード」で切り替えられ、選択はブラウザーに保存されます。

| モード | 内容 |
|---|---|
| 予測 | 開いていそうな店舗と、その日出るメンバーの割り振りを出します。メイドさんは予測した店舗順に並びます |
| 誰いるか | 店舗の予測をすべて隠し、誰がお給仕に出るかだけを見ます。並びは `roster` の公式順です |
| この人はどこ | メイドさん1人ずつに、その月どこに立ちそうかを日付順で並べます（人 → 日付 → 店） |
メイドの絞り込みには「**キッチンにゃんこを除く**」チェックがあります。チェックすると `kitchenStaff` の5名をカレンダーから隠します（店舗の見込みと割り振りは変わりません。裏側では全員で計算しています）。リセットで解除されます。

カレンダーの昼・夜それぞれに、その時間帯にどの店舗が開いていたか（開きそうか）を表示します。バッジは4種類で、**確かなものから順に**採用します。

| バッジ | 意味 |
|---|---|
| 実績 | 公式Xの投稿で確認できた、その日そのシフトの営業店舗 |
| 翌日見込み | 前日の同じシフトの実績から、ローテーションで見積もった値 |
| 同日の実績 | **同じ日のもう片方のシフト**の実績から見積もった値 |
| 曜日傾向 | 曜日ごとの過去1年の営業率。その日の予測ではありません |

見込みは**記録の最終日以降にしか出しません**。過ぎた日にたまたま記録が無いのは「休みだった」ではなく「記録が無いだけ」なので、そう断ります。記録は昼だけ・夜だけ入ることがあるため、判定は日ではなくシフト単位で行います（例: 昼だけ記録のある日の翌日は、昼が見込み・夜が曜日傾向になります）。

### 記録のある日は、記録の顔ぶれを出します

**「実績」バッジが付くシフトでは、予定表からの割り振りをいっさい使いません。**`insights.actualRoster` にある「誰がどの店にいたか」をそのまま出します。店だけ記録で名前は推測、という混ざった状態にはしません。

**その日の顔ぶれは記録がすべて決めます。** 予定表に名前があっても記録に無ければ出しません。実際に 9/1 夜の `まこっちゃん`、9/2 昼の `るるか` がそれで、**お休みだった方を「どこにいるか分からない」と書くのは嘘**になります。逆に、記録にしかいない方（予定表に載らない見習いなど）は出します。

並びは公式の掲載順のままです。**`roster` に無い方は、その後ろに記録の並びで置きます。**この方たちにはメイド絞り込みのチェックボックスがないので、**絞り込みを始めた時点で隠します**（＝全員選択のときだけ出ます）。チェックボックスの無い名前が絞り込みをすり抜けると、「1人だけ選んだのに他の名前が出る」ことになるためです。

記録の日には、メイドさんの行に**確率を出しません**。誰がどこにいたかは分かっているので、`title` も「◯号店にいた記録があります」になります。

### 見習いにゃんこには 🔰 を付けます

`actualRoster` の `trainees` にいる方に 🔰 を添えます。絵文字だけに頼らないよう、行は破線の枠（`.is-trainee`）にし、`title` と `aria-label` に「見習いにゃんこ」と書きます。🔰 自体は `aria-hidden` で、読み上げは行のラベルが担います。

**`trainees` キーが無い日には、誰にも印を付けません。**直近120日より前は判定していないためで、これは「全員が昇格済み」ではなく「**分からない**」です。実装でも `?? []` で潰さず、キーの有無で分けています（潰すと、その区別が黙って消えます）。判定の中身は[見習いにゃんこの見分け方](#見習いにゃんこの見分け方)にあります。

### まだ予定を出していない方がいることを言います

**予定表が実際より薄い理由は、これで全部説明できます。**在籍39名のうち7名が未提出で、うち2名は直近ほぼ毎日お給仕に出ています。

```
予定表 8.3人 + 未提出ぶん 1.8人 = 10.1人   記録 9.85人
```

カレンダーの下に1行出します。詳細（誰が未提出か・最近の出番）はツールチップと読み上げに入ります。

> 在籍39名のうち7名が、まだ予定を出していません

**推定で埋めません。**誰が抜けているかは分かりますが、その人が今月何日出るかは分からず、提出が進むぶん補正を減らす仕組みも要ります。**「揃っていない」と言うほうが、揃えば自動で黙る**点でも正しい形です。`schedulePending.pending` が空になれば消えます。

**「何人ぶん薄いか」は `schedulePending.windowShifts` で割って出します。**分母がデータに入っているので推測になりません（328回 ÷ 177シフト ＝ 1.9人）。**入っていなければ書きません。**推測した分母で割った数字は、測った数字の顔をしてしまいます。テストは「印字した値が `windowShifts` から出たものと一致すること」を見ているので、別の窓で割ると落ちます。

既存の[制度変更の注意書き](#店舗の見込み表示)は「出していない人がいることがある」までしか言えず、日数で自動的に引退します。こちらは**実際に誰が出していないかを見て**出るので、両方が並びます。

### 開く店の数が表の上限に当たったら、そう断ります

店舗数は `openCountByHeadcount` を引いて決めています。この表は「何人を超えたら1店増えるか」の区切りなので、**言える最大は要素数+1**です。いまは2要素なので3店までしか答えられません。

3要素目が無いのは、**記録に4店のシフトが一度も無い**からです（昼360件・夜360件に0件）。「4店にはならない」と測ったわけではありません。実際、2026-09-03の昼はお店から4店営業の案内が出ています。

そのままだと画面には「3店」としか出ず、**3店が最有力だと読まれます**。そこで**予測した店舗数が上限と等しいとき**に断りを出します。

```
1号店   3号店   4号店
3店までしか数えられません
```

ツールチップと読み上げには理由まで入れます。

> この昼は3店で、いまの表で言える上限です。3店より多いシフトは昼360件の記録に0件しかありません。**3店がいちばんありそう、という意味ではなく**、これより多いかどうかを数える材料がありません

**上限も件数も表から引きます。**`openCountByHeadcount` の要素数と `openCountPerShift` の分布で決まるので、記録が増えれば文言も追随します。テストも同じ引き方をするので、数字を書くと落ちます。

記録のあるシフトには出しません（実際に何店開いたか分かっています）。上限が全店に届いている場合も出しません（それ以上の店が存在しないので、数えられないものがありません）。

**閾値の表そのものは増やしていません。**3要素目を入れれば2026-09-03の昼は当たりますが、**そのぶん28シフトを落とします**。

| 表 | 店舗数の的中 | 4店と言った回数 | うち当たり |
|---|---|---|---|
| `[5, 12]`（現行） | **87.5%** | 0回 | 0回 |
| `[5, 12, 13]` | 82.2% | 28回 | 0回 |
| `[5, 12, 14]` | 83.3% | 20回 | 0回 |
| `[5, 12, 16]` | 86.7% | 6回 | 0回 |

記録353シフトのうち、`roster` の人数が13人を超えたのは28件です。**そのすべてで実際は3店以下**でした。1件を当てるために28件を落とす取引になります。

なお**表を増やせば4店は出ます**。9/3の昼（14人）は `s1・s2・s3・s4` になり、お店の案内（ちゆ1号・ちょこ2号・ちま3号・ねむり4号）と一致します。**店の順位づけは合っていて、数だけが表で止まっています。**

### 店ごとに独立して判定する案

「4店舗を独立に集計すれば上限が消えるのでは」という案も測りました。**1店ずつの精度は保たれますが、店舗数が壊れます。**

| 方式 | 組が一致 | 店ごと | 店舗数 |
|---|---|---|---|
| 現行（人数→上位N店） | **48.3%** | 76.1% | **88.1%** |
| 独立（曜日・人数・前日） | 36.4% | 74.9% | 64.0% |
| 独立＋配属者の人数 | 39.0% | **76.5%** | 61.9% |
| 独立＋配属者の人数と割合 | 34.7% | 74.6% | 58.9% |

**現行方式の強さは「何店開くか」を88.1%で当てているところ**にあります。独立に切ると「だいたい2店」という制約が使えなくなり、店舗数が62%まで落ちます。顔ぶれの配属を足すと「店ごと」は現行を上回りますが（76.5%）、店舗数は戻りません。

独立方式は閾値を下げれば4店を出せますが、**9/3の昼を流しても4店になりません**（`s1 98% / s2 30% / s3 32% / s4 22%`。4号店は前日開いていて配属者も3人いるのに22%）。**どの方式でも、いまある記録からは当てられない日**でした。


### 昼の記録から、夜の行き先を読み直します

**通しで働いた方の68.7%が、昼と別の店にいます。**昼の店が夜も開いていた場合でも56.4%が移るので、「所属店が開いているから残る」ではありません。移り先には向きがあり、夜はどの店からも1号店に吸われます。

| 昼の店 | 夜に1号店 | 夜も同じ店 |
|---|---|---|
| 2号店 | 66% | 24% |
| 3号店 | 76% | 21% |
| 4号店 | 84% | 2% |

`insights.sameDayMaidMove`（全体）と `maidTendency[名前].sameDayMove`（人ごと・39名中25名）を使い、**その人の傾向に移り先の確率を掛けます**。

```
score(店) = その人の夜の傾向(店) × 移り先の確率(昼の店 → 店)
```

**置き換えず、掛けます。**置き換えると「夜はみんな1号店」になって、その人の癖が消えます。掛けた結果が全滅したとき（その店に移った記録が1件も無い場合）は傾向だけに戻します。**移り先が読めないことと、行かないことは違います。**

**昼が実績のときだけ使います。**昼が見込みだと、推測した店の誤差が夜にも乗ります。夜も実績なら、そもそも割り振りが要りません。実測で夜の行き先の的中が **62.2% → 69.0%** に上がります（574件・92勝53敗・p=0.0015）。

移り先を使った行には、**なぜ移るのかも書きます**。「3号店にいたのに、3号店が開いている夜に1号店」は読み手が実際に持った疑問なので、移り先だけ出すと同じ疑問が残ります。

### キッチンにゃんこは、見込みの日には店を名乗りません

見込みのシフトでは、キッチンにゃんこを店ごとの一覧から外し、専用の見出しの下に置きます。**名前は出します**（予定表に載るので、誰が出るかは分かります）。分からないのは、どの店にいるかです。

理由は2つあります。

**当てられません。** 実測の確度はフロア65.4%に対しキッチン58.7%です（うる52% / みりん55% / まこっちゃん61% / けだま62% / あらた65%）。

**当てる必要もありません。** 開いた店の枠にキッチンが載っているのは90%（1号店83% / 2号店99% / 3号店100% / 4号店95%）で、1店なら1人・2店なら2人と各店1人ずつです。「どの店にいるか」は「どの店が開くか」とほとんど同じことしか言っていません。掛け持ちは1470件中16件だけです。

**店舗チップも出しません。**「店を名乗らない」と決めた以上、チップで名乗ると見出しと矛盾します。

**記録のあるシフトと、記念日の主役は変えません。**どちらも実際にどこにいたか・どこにいるかが分かっているためです。

**店舗数の計算からは外しません。**キッチン人数だけで店舗数を当てると80.9%、総人数なら92.9%です。総人数に入れたままがいちばん当たります。

並びは**店ごとの一覧 → 見習い → キッチン**です。上ほど確かなことを言っています（見習いは「誰か分からないが、いる」、キッチンは「誰か分かるが、どこか分からない」）。

### 見込みのシフトにも見習いにゃんこを数えます

**見習いは予定表に名前が出ません。**そのままだと、まだ記録の無いシフトは実際より人数が少なく出ます。`insights.traineeOutlook` の「1店あたりの人数」に、開くと見込んだ店の数を掛けて丸めた人数を足します。

| 開く店 | 昼 | 夜 |
|---|---|---|
| 1店 | 0人 | 0人 |
| 2店 | 1人 | 1人 |
| 3店 | 1人 | 1人 |
| 4店 | 2人 | 2人 |

**名前は出しません。**誰なのかが分からないので「**見習い🔰**」と書き、読み上げにも「どなたかは分かりません」と入れます。同じ表示が複数並ぶことがあります。

**どの店かも出しません。**1店あたりの実測は1号店0.35 / 2号店0.35 / 3号店0.32（昼）と横並びで、どこかを選ぶ根拠がありません。店の見出しの下に置くと「その店にいる」と読まれるので、**店ごとのグループの後ろに、店を名乗らない一覧として置きます**（`.maid-trainee-list`。`.maid-list` は「見出しと1対1」を保つ約束があるので混ぜません）。枠は点線にして、実在の記録より弱く見せます。

**記録のあるシフトには出しません。**誰がいたか分かっているところに推測を混ぜる理由がありません。

**割合そのものは画面に書きません。**見習いの数は入店で動くので、データ側は半減期30日で見ています（人数の180日とは別）。落ち着いた量ではなく、来月には変わります。同じ理由で、テストも期待する人数を表から引き直しています。

なお**店舗数の判断には見習いを入れていません**。閾値 `openCountByHeadcount` は見習いを除いた人数で作ってあり、足すと両側がずれます。また見習いの人数は店舗数から出しているので、店舗数の判断に使うと循環します。

なお**既定の表示範囲は当日から始まる**ので、昨日までの記録は既定では画面に出ません。開始日を戻すと出ます。

**同じ数字でも、根拠の重みは違います。** 「翌日見込み」は前日の実績を踏まえた値で、本文にその日付を名指しします。「曜日傾向」は前日が分からないときの値で、本文に「前日の実績が手元にないので」と書きます。**いま予定表に出る30シフトのうち、前日の実績があるのは2件だけ**です。記録は手入力した日しか増えないので、1日ぶん実績が分かると**その翌日1日だけ**が良くなります。

**「同日の実績」は2・3号店にだけ使います。** 昼に2号店が開いていれば夜も2号店で、3号店に入れ替わることはほぼありません（`rotation.sameDay.s2.s3` は該当0件）。ところが曜日傾向にはこの情報がなく、2号店と3号店がどちらも3割前後で並びます。実測で、夜の店舗の組み合わせを丸ごと当てる的中が **23.8% → 30.4%**、2号店の F1 が **5.7% → 39.6%** に上がりました（n=349、McNemar p=0.015）。

1号店と4号店は曜日傾向のままです。4店すべてに同日ルールを当てると、4号店の F1 が 51.2% → 46.3% と落ちます。4号店は片シフトだけの営業が84%で、昼に開いていたら夜は閉まる傾向があるのですが、その効きが強すぎて、夜だけ開く日を取りこぼすためです。

**このルールは「昼の実績 → 夜の見込み」の向きにしか使いません。** `rotation.sameDay` はその向きに作られた表で、逆に当てると別の分布になります。記録176日で見ると、夜が2号店だった日の昼は2号店が58%ですが、この表を流用すると40%と出ます。夜だけ記録のある日（稀です）は曜日傾向に落とします。

なお記録の最終日で欠けているシフトには、「記録だけが手元にありません」と書きません。取りこぼしたのではなく**まだ来ていない**ためです（今日の昼が入った時点で、夜はこの見込みに切り替わります）。

### 表に出すのは店の名前だけです

**開くと見込んだ店のバッジだけを出し、確率は表示しません。** どの店を開けるかは当日決まるので、4店ぶんの数字を並べても読み手は選べません。並べるほど「52%と42%を足して94%」のような読み方も招きます。

- **バッジが出るのは、開くと見込んだ店だけ**です。その店に顔ぶれを割り振ります
- 僅差で選ばれなかった店は「**かも**」を付けて、破線の枠で出します。無視したのではなく、まだ決まっていないためです
- **数字は HTML に残しています。** 4店ぶんの割合・根拠・較正・母数は、ツールチップと読み上げ用テキスト（`.visually-hidden`）にすべて入っています

メイドさんの行にも割合は出しません。店舗ごとの見出しがその店を名乗っているので、行に繰り返す意味がないためです。見出しと違う店に割り振られた人だけチップが付きます。行の `title` には、その人の全店の確率と根拠が入ります。

### 「この人はどこ」モードの注意

**日付は行ごとに書きます。**日付を見出しにして昼・夜を束ねる形も試しましたが、**片シフトだけの日が83%**（223件中190日、通しは33日）なので、ほとんどの見出しが1件しか抱えません。入れ子が増えるだけで、読み手には同じことしか伝わりませんでした。曜日はカレンダーと同じ書き方で添えます（「9/3」だけでは何曜日か分かりません）。

```
あむ  12件
  9/3(木) 昼   3号店
  9/3(木) 夜   3号店
  9/4(金) 夜   1号店
```

**同じ精度でも、縦に並べると外れが見えます。** 店ごとの画面では1行ずつ独立に見えるので気になりませんが、同じ人の見込みを日付順に並べると、外れが一覧で目に入ります。だから各ブロックの冒頭で、**当てに行っている件数と「全部当たる」確率**を先に断ります。

**確度はその人ごとの実測を使います。**`maidTendency[名前].accuracy` に `{ rate, n }` があります。直近180日の各シフトを、その手前120日だけを見て答え、実際と突き合わせた値です（1店しか開かなかったシフトは定義上かならず当たるので除外）。

> この方の行き先は過去89件を試して67%当てられていますが、6件すべて当たるのは9%です。

- **人によって39%〜81%と幅があります。**全体値（65.6%）で代用すると、当てにくい方を実際より当たるように、当てやすい方を実際より当たらないように書くことになります
- **母数（`n`）も出します。**36件で81%と148件で76%は、同じ確からしさの主張ではありません
- **測れていない方には、全体値で埋めません。**記録が20件に満たない方が1名います。その方には「測れていません」と書きます
- 記録や記念日で確定している件数は、この計算から外します

**主語はこちら側に置きます。**「この方は読めません」ではなく「**私たちが当てられませんでした**」です。キッチンにゃんこのように低く出る方がいるので、そこは書き方で担保します。

以前は `spread`（行き先の偏り）を代理指標として3段階に言い分けていましたが、**実測が入ったので置き換えました**。「当たりやすい側です」は読み手に順位を信じてもらう形ですが、「89件試して67%」なら読み手が自分で判断できます。

**確度の低い日を空欄にしません。** 空欄は「その日は出ない」と読まれます。割り振り先が決まらなかった日は「**未定**」と書きます。

**行ごとの営業率は本文に書きません。** 店を選ぶときには予定表の顔ぶれも見ているので、営業率だけを出すと「25%の店になぜ置いたのか」と読めてしまいます。確からしさは枠線と「かも」で伝え、数字は `.maid-plan-rate` として HTML に残します。

### どの店を開けるかは当日決まります

**この区別が、このサイトの精度の上限を決めています。**

| | いつ決まるか | 読めるか |
|---|---|---|
| **何店開くか** | 事前（お店が人を組む時点） | **87.5%**。断定してよい |
| **どの店か** | 当日 | 50%が上限。断定できない |

裏づけです。同じ日に昼夜とも出た1234人のうち、**68.6%が昼と夜で別の店**にいました。店の開き方も、1号店だけが日単位（93%が通し）で、2〜4号店は片シフトだけの営業が主です（4号店は84%）。**シフトごとにその場で割り振っている**形です。

だから精度がここで止まります。

```
素の割合         34.4%
曜日から         36.8%
予定表の配属者数   41.1%
前日から         46.2%
前日＋配属者数    50.9%   ← 上限
```

**当日決めているものを事前に当てているので、50%で止まるのが当然**です。推定が下手なのではなく、決定がまだ行われていません。前日が効くこととも矛盾しません。前日と同じ店を続けるのは1〜2割で、「当日、前日と違う店を開ける」という決め方なら両立します。

そこで画面では、**「予測を外した」ではなく「まだ決まっていない」**と書いています。見込みのシフトにはかならずこの一文が付きます。

> 何店開くかは、その日に出る人数から読めます（お店が先に人を組むため）。ただし、どの店を開けるかは当日決まります。ここから先は過去の並びから見た可能性で、まだ誰も知りません。

### 2番手の店は、予定表の顔ぶれから読みます

上の3つはどれも**実績を必要とします**。ところが記録は 8/30 で止まっており、予定表15日のうち前日が分かるのは1日だけです。残りは曜日傾向しか無く、2・3・4号店がどれも2割前後で並んで意味をなしていませんでした。

**その日の予定表に、各店を本拠とする人が何人載っているか**は実績なしに分かります。これが効きます。

| その店の配属者 | 0人 | 1人 | 2人 | 3人 | 4人 |
|---|---|---|---|---|---|
| 2号店が開く | 27% | 28% | 31% | 45% | 54% |
| 3号店が開く | — | 23% | 28% | 28% | 48% |
| **4号店が開く** | 37% | 35% | 33% | 38% | **30%** |

2番手を当てる的中が **34.4% → 42.2%**（372シフト、87勝58敗、p=0.020）。前日の実績が分かる日は併用して50.9%です。

**4号店は、この見方では読めません。** 配属者が0人でも4人でも3割前後で、動く方向すら一定しません。

**キッチンにゃんこは、この数に入れません。** 公式サイトには配属が載っていますが、実測ではその店に入る率がフロアより13.3ポイント低く（62.6% 対 75.9%、n=5対34、並べ替え検定 p=0.025）、どこにでも入っています。実際 `うる`（配属3号店）と `みりん`（配属1号店）は、どちらも実績の最多が4号店です。外すと表が鋭くなります（3号店の振れ幅が21%→54%）。**予定表に出ているキッチンにゃんこを数に入れていないので、画面の顔ぶれを数えると合いません。** その旨をツールチップに書いています。

なお「4号店が読めないのはキッチンが混ざっているからでは」という見立ては**外れ**でした。除いても振れ幅は9%→8%とほぼ変わりません。キッチン5名に4号店配属が一人もいないためです。

ただし**「4号店は読めない店」ではありません。** 読めないのは「空いた1枠を誰が取るか」のほうだけで、**4号店が開くかどうかは他店から読めます**（同時に2号店が開くなら7%、開かないなら38%）。この違いは下の「4店の関係」を参照してください。

**置き換えではなく、平均からのずれ（尤度比）で元の見込みを更新します。** 置き換えると、同日ルールが出した「昼が2号店なら夜の3号店は1%」のような強い手がかりまで捨ててしまいます。この形なら、表が平均どおりの店は動かないので、**4号店がこの見方で読めないことも特別扱いせずそのまま出ます**。同時に、同日ルールや前日ローテーションが出した4号店の見込みは保たれます。開く店の数の見込みも変えず、3店のあいだの配分だけを動かします。実績の日と、記念日で営業が確定した店には触れません。

### 4店の関係

**1号店は独立、2・3・4号店は三つ巴**、というのが実態です。同じシフトで同時に開いた回数を、無関係だった場合と比べます（357シフト）。

| 組み合わせ | 実際 / 無関係なら | φ係数 |
|---|---|---|
| 1号 × 2号 | 108回 / 108回 | −0.008 |
| 1号 × 3号 | 106回 / 106回 | −0.010 |
| 1号 × 4号 | 114回 / 114回 | −0.002 |
| 2号 × 3号 | 7回 / 34回 | **−0.353** |
| 2号 × 4号 | 9回 / 36回 | **−0.353** |
| 3号 × 4号 | 12回 / 36回 | **−0.307** |

**1号店は他店と完全に無関係**で、開くか閉まるかの話に一切関与していません。**2・3・4号店は3組とも同じ強さで避け合います。** 「2号店と3号店が排他」という言い方は、4号店を外している点で不正確です。

```
2・3・4号店のうち何店開くか      その1店の内訳
  1店   281回  78.7%            4号店  96回  26.9%
  0店    48回  13.4%            2号店  95回  26.6%
  2店    28回   7.8%            3号店  90回  25.2%
```

つまり **「1号店 ＋ 2/3/4 のうち1店」** が基本形で、その1枠を3店がほぼ均等に分け合っています。だから4号店の営業率は、他店の状況で大きく動きます。

| 1〜3号店のうち開いた店数 | 4号店の営業率 |
|---|---|
| 1店（＝1号店だけ） | **63.3%** |
| 2店 | 10.5% |
| 3店 | 0% |

メイドさん1人ずつには、その日いそうな店舗を小さなチップで表示します。**1人ずつ独立に判定すると、ほぼ毎日開いている1号店に全員が寄ってしまう**ため（`share` の最上位は roster 全員が1号店でした）、その日そのシフトに出る顔ぶれを、**店ごとの標準人数を定員として割り振っています**。定員は `typicalHeadcount` の比で決め、迷いの少ない人から順に席を取ります。絞り込みを変えても割り振りは動きません。

> **`share` と `pickRate` は用途が違います。取り違えると必ず全員1号店になります。**
> `pickRate[s]` は「その店が**開いていた日**に、その人がそこに入った割合」。
> `share[s]` は「その人が出勤する日に、その店にいる確率」で、**営業率で重み付け済み**です。
> 1号店はほぼ毎日開くので、`share` は誰でも1号店が最大になります。**個人がどの店にいそうかを見るときは、かならず `pickRate` を使ってください。** この罠は集計側でも一度踏んでいます（「全員の最多店が1号店」という結果が出たら、まず `share` を使っていないか疑ってください）。

**チップの数字は確率です。断定ではありません。** 「この人はこの店」と決め打ちすると、たまにしか入らない店を必ず取りこぼします。実際、決定的に割り当てていたときは**4号店にいた256回のうち103回（40%）を外していました**。`ひかり`（4号店の pickRate 0.09）や `ひなり`（0.03）は10回・8回とも全部外しています。

しかし実測では**在籍39名全員が4店舗すべてに入った実績があり**、4号店の pickRate もいちばん低い人で0.018と、ゼロではありません。そこで候補店の中で `pickRate` を合計1に正規化し、**どの店も0%にならない**ようにしています。その日の候補店に絞ったときの的中は上位1店で62.1%、**上位2店なら97.2%**です（4店すべてを候補としたときは `accuracy.maidStoreTop1` / `maidStoreTop2` の53.2% / 75.0%）。

**較正は真ん中では良いのですが、端は当てになりません。** 「40〜49%」と出したときの実測は44.7%ですが、**「90%以上」と出したときの実測は75.6%**です。

| 出した確率 | 件数 | 実測 |
|---|---|---|
| 0〜9% | 241 | **21.2%** |
| 10〜19% | 594 | 20.4% |
| 20〜29% | 974 | 24.8% |
| 30〜39% | 1371 | 31.7% |
| 40〜49% | 1634 | 44.7% |
| 50〜59% | 1543 | 57.6% |
| 60〜69% | 1118 | 67.8% |
| 70〜79% | 674 | 72.1% |
| 80〜89% | 385 | 74.0% |
| 90%以上 | 160 | **75.6%** |

20〜79% の範囲は5ポイント以内で収まりますが、**両端では自信が過剰**です。「6%」と出した店に実際は2割の割合で入っていますし、「94%」と出しても4回に1回は外します。上位2店を併記しているのはこのためで、**いちばん高い数字だけを鵜呑みにしない**でください。

この表は `accuracy.calibration` に入っています。**`tools/data/shifts.csv` だけで計算できる**ので、集計期間や重みを変えて再生成すれば追従します（訓練に直近120日を使い、その先の期間を評価する形で遡って測っています）。README の他の的中率と違い、**この数字はリポジトリの中で検算できます**。

**ただし測っているのは「2店舗以上開いた日」だけです**（`scope: "twoOrMoreOpen"`）。1店舗しか開かない日は、その人がその店にいるのが定義上100%になり、表を不当に良く見せるためです。**候補店が1つでチップが100%と出るときの不確かさは「店舗予測が当たるか」であって、この表の数字ではありません。** 実測では1店舗と見込んだシフト137件のうち、その人が予測した店にいたのは87.2%でした（2店舗のときは72.5%）。候補が1つに絞れるほど人数が少ない日は「1号店だけ」という明快な形が多く、かえって当たります。

なお公式サイトの配属を事前分布に入れたことで、この較正は少し改善しています（Brier 0.2192 → 0.2170、いちばんのずれ 26.8 → 22.8ポイント。全履歴で測った値）。端の確率を均等側へ2割ほど寄せるとさらに縮みますが、これは「90%と言わなくなる」効果が主で、最適な寄せ幅も集計期間で動くため入れていません。上位2店を併記している以上、数字を歪めるより注記で断るほうが情報が減りません。

狭い月グリッドでは最有力の店だけを出し、モバイル幅とツールチップには**候補店すべての確率**を並べます。並び順は割り振り結果（店ごとのまとまり）に合わせているので、チップの先頭はその人が入っているグループの店です。ツールチップには**公式サイトの配属**も添えます。確率は実績が主で配属は弱い事前分布なので、記録が積み上がった人ほど表示は配属から離れます。そのずれを読み手が確かめられるようにするためです。

**上の較正はツールチップにも出しています。** 表示した確率が実測と10ポイント以上ずれる帯（両端）に落ちたときだけ、「90%以上と出したときに実際に当たったのは76%です（開いた店が分かっている日で測った値なので、開く店の予測を外すぶんは含みません）」のように断ります。真ん中の帯では何も足しません。帯の境目は `accuracy.calibration` から計算しているので、再生成すれば追従します。標本が100件に満たないバケットは実測値自体が揺れるため、注記の根拠にしません。

**候補店が1つのシフトでは、この数字を引きません。** `scope` が `twoOrMoreOpen` なので、測っていない領域だからです。代わりに「この夜は1号店だけが開く見込みなので、その見込みが当たればこの店です」と、100%の出どころを構造で説明します。裸の100%を見せないためで、かつ不確かさの在り処（店舗予測が当たるか）を正しく指しています。`scope` を別の値に変えたり `minOpenStores` を足したりすれば、`app.js` を触らずに判定が変わります。

**生誕祭・周年・卒業の主役だけは確実です。** 主役はかならず自分の所属店に立つため、その人は割合ではなく「確定」と表示し、**その店はその日営業することも確定**として扱います。所属店は公式サイトの配属（`data/schedule.js` の `homeStore`）を使います。公式に載っていない人だけ、その店が開いた日にいちばん入っている店（`home`）からの推定で補います。

公式の配属と実績からの推定は**別物**である点に注意してください。在籍39名のうち4名（`える`・`あめる`・`みりん`・`ゆめ`）は、配属先と「実際にいちばん入っている店」が食い違います。前者は所属、後者はヘルプを含めた実態です。

**所属の出どころは2種類あります。** 公式サイトのメイドさん紹介に載っている35名はサイトの配属、まだ載っていない4名（`unpostedMaids`）はお店からの案内です。ツールチップも「公式サイトの配属は2号店」「お店の案内による所属は2号店」と書き分けます。突き合わせられる相手が違うので、同じ顔で出しません。

**お給仕の記録が薄い人は、公式サイトの配属に寄せています。** `pickRate` は「その店が開いていた日のうち、その人がその店にいた割合」ですが、記録が数回しか無い人ではこの割合が当てになりません。そこで公式の配属を**2回の出勤ぶんの重みを持つ事前分布**として混ぜ、記録が増えるほど実績が勝つようにしています（`build-insights.py` の `POSTED_PRIOR`）。

| その人の記録 | n | 事前分布なし | あり | 差 |
| --- | --- | --- | --- | --- |
| 0回（初出） | 145 | 66.2% | **73.1%** | +6.9pt |
| 1〜5回 | 296 | 51.4% | 55.1% | +3.7pt |
| 6〜15回 | 456 | 59.0% | 59.4% | +0.4pt |
| 16〜40回 | 1046 | 70.2% | 70.7% | +0.5pt |
| 41回以上 | 3822 | 66.7% | 66.8% | +0.1pt |
| 全体 | 5765 | 65.9% | 66.5% | +0.6pt（McNemar p=0.037） |

**記録の多い人はほとんど動かず、薄い人だけが大きく上がります。** 41回も出ていれば本人の実績のほうが強い情報なので、これが望ましい形です。一律に下駄を履かせる方式も試しましたが、全体の的中はほぼ同じで、記録の多い人の数字まで動いてしまうため採っていません。重みは0.5〜2.0が有意で、3.0以上は有意になりません。

これがいちばん効くのは、**3か月の見習い期間を終えたばかりの人が `roster` に入ったとき**です。実績がまだ1件も無い状態でも、初日から配属店を出せます。公式サイトに載っていない人（`unlistedMaids`）は従来どおり実績だけで出します。

**キッチンにゃんこは各店1人ずつが基本です。** 実測で1店1人が77.5%（平均1.05人）、キッチン同士の同店率は中央値19%（全ペアの中央値50%に対して）でした。割り振りでは、主役の次に優先して席を決め、すでにキッチンがいる店には減点をかけます。禁止ではありません（実際に13.7%は2人一緒です）。後回しにすると定員が埋まって同じ店に押し込まれてしまうため、順序が重要です。

なお、**この節に書いた精度や根拠はサイトには表示していません。** カレンダーの下に長い解説を出しても冗長なので、バッジと店舗チップのツールチップ（およびスクリーンリーダー向けの読み上げテキスト）に必要なぶんだけ載せ、詳細はこの README に集約しています。

### 予測精度（実測値・正直な注記）

**このサイトの「見込み」は当たりません。** 実測値は次のとおりです。

- 翌日について「2号店と3号店のどちらが開くか」は、昼夜をまとめて **51.4%**（当てずっぽうは 38.3%）
- **昼夜まで分けると 2・3号店は昼 38.3% / 夜 43.0%** で、当てずっぽうと変わりません
- 4号店の翌日は昼 63.6% / 夜 70.1% で、こちらは多少あてになります
- **2日以上先はベースライン並み**です。曜日ごとの平均を出しているだけで、その日の予想には使えません
- メイドさんの店舗を1店に絞って当たるのは、開いている店舗が分かっていれば 65.6%、分からなければ 53.2%（「常に1号店」の 54.2% と同等）。**候補を2店舗まで広げると 75.0%**
- 生誕祭・周年・卒業の日は主役のメイドさんが顔ぶれを選べるため、傾向の計算から除いています

ローテーション表は2種類あります。チップの数値には**シフト別**の `rotation.nextDay` を使い、日単位の `rotation.nextDayByDay` は「その日どちらの店が開くか」という補足にだけ使っています。日単位の表をシフト別の予測に流用すると昼は 38.3%→43.9% と改善しますが夜は 43.0%→33.6% と悪化し、合計ではほぼ同等（n=107）だったため、シフト別のままにしています。

### 何店舗開くかは人数から決めています

開く店舗の数は日によって違います。**昼は1店舗が18.0%・2店舗が74.0%・3店舗が7.5%、夜は1店舗が26.9%・2店舗が68.4%・3店舗が2.2%**で、夜のほうが閉まりやすい傾向です。

**ローテーションの確率からは、この店舗数を当てられませんでした。** 1号店の営業率が高すぎて、確率を足しても閾値で切ってもほぼ常に「2店舗」になり、実際にある3店舗の日も1店舗の日も出せません（実測で的中 24〜34%）。

代わりに、**その日カレンダーに出る人数**から決めています。実測では開いた店舗数ごとの人数がはっきり分かれます。

| 開店店舗数 | 昼の人数 | 夜の人数 |
|---|---|---|
| 1店舗 | 4.32人 | 4.26人 |
| 2店舗 | 9.06人 | 8.47人 |
| 3店舗 | 13.33人 | 12.75人 |

`typicalHeadcount` の累積がその日の人数に届くまで店舗を足す、という方式で**昼84.4% / 夜91.8%**の的中でした。ただし**1号店の昼が6.1人あるため、6人が1店舗と判定されてしまう**問題がありました。実測では6人は昼61% / 夜73%で2店舗が多数派です。

係数を掛けたり `p25` を使ったりすると6人は直りますが、上の境界が崩れて12人が3店舗になり、全体の的中が77%に落ちました。そこで**人数ごとの多数決を実測して境界そのものを持たせています**（`openCountByHeadcount`）。

| 人数 | 昼 | 夜 |
|---|---|---|
| 〜5人 | 1店舗 | 1店舗 |
| 6〜 | 2店舗 | 2店舗 |
| 15〜 | 3店舗 | 13人〜 3店舗 |

これで的中は**昼88.9% / 夜93.2%**になりました。`typicalHeadcount` は見習い込みの人数なので、カレンダーに出る在籍だけの人数と直接比べると1割ほどずれます。

なお2店舗に割れるときの人数配分は `typicalHeadcount` の比で決めています。**4号店は4人態勢**なので、6人のシフトなら「1号店4人 + 4号店2人」という実測最多の形になります。

見習いは店ごとに 1号店0.83人 / 2号店1.22人 / 3号店0.95人 / 4号店0.59人います。**4号店だけ少なめ**で、見習いがいないシフトが43.1%あります。

### どの店が開くかは顔ぶれの配属先から決めています

何店舗開くかが決まったら、次は**どの店か**です。以前は曜日別の営業率の高い順に選んでいましたが、いまは**その日出るメイドさんの配属先**を見ています。「この日この人たちが出るなら、この号店が開く」という見方です。

顔ぶれのうち2号店配属の人が平年（`homeStaffShare`）より多ければ2号店の順位を上げ、少なければ下げます。**店舗の組み合わせを丸ごと当てる的中は 42.9% → 47.7%** になりました（n=709、McNemar p<0.05）。

たとえば9月10日の昼は、出勤9名のうち**2号店配属が1人もいません**（4号店3名・1号店3名・3号店3名）。営業率だけで並べると2号店を選びますが、顔ぶれを見れば4号店です。

**人数ではなく割合で見ています。** 予定表の提出が揃っていない時期でも比が変わらないためです。顔ぶれを伏せた条件でも改善が続きます。

| 方式 | 欠けなし | 15%欠け | 30%欠け |
|---|---|---|---|
| 曜日別の営業率だけ（以前） | 42.9% | 41.5% | 36.0% |
| その日の人数も使う | 47.2% | +2.8（10/10） | **+0.0（5/10）** |
| 誰が出るかを学習して使う | 49.5% | +3.7（10/10） | **+0.5（6/10）** |
| **配属先の割合を使う（現行）** | **47.7%** | **+3.5（10/10）** | **+2.5（10/10）** |

括弧内は、間引く人をランダムに選ぶ乱数の種を10通り変えたときに**改善した回数**です。欠け条件の数値は種によって数ポイント動くので、1回の測定では判断できません。

「誰が出るか」を学習した係数のほうが、予定表が揃っていれば最良（49.5%）です。ただし**3割欠けると当たり外れが半々になり**（10回中6回しか改善しない）、頼れなくなります。配属先の割合を使う方式だけが10回とも改善しました。公式サイトから読める情報だけで済み、説明もしやすいところも利点です。

移行が終わって予定表が揃ったら、学習係数版（49.5%）への切り替えを再検討する価値があります。

#### 選ぶときと出すときで、同じ数字を使います

この顔ぶれの傾き（`applyPostedTilt`）は、**画面に出す割合そのものを動かします**。以前は `expectedOpenStores` が順位づけのときだけ内部で足していて、表示される割合には入っていませんでした。結果として

```
2026-09-09 昼  選ばれた店 1号98% + 3号37%   空いている店 4号40%
2026-09-12 夜  選ばれた店 1号90% + 4号26%   空いている店 2号26% / 3号26%
```

のように、**高いほうが空で、低いほうに顔ぶれがいる**表示が28シフト中5件出ていました。読み手には理由が見えません。

どちらが正しいかは実測できます。過去1年521シフトで、実際に開いた店をよく当てるのは**顔ぶれを入れた順位のほう**でした（1.36店 対 1.32店。食い違った104件で45勝25敗、二項検定 p=0.023）。つまり**直すべきは順位づけではなく、古いままだった表示のほう**でした。

いまは対数オッズで傾けた値をそのまま表示し、`expectedOpenStores` はその割合を上から採るだけです。傾け方を順位づけと同じ式にしてあるので、**選ばれる店は1件も変わらず**（30シフトで差分0）、食い違いだけが5件→0件になりました。テストでは「選ばれなかった店の割合が、選ばれた店の最小を上回らないこと」を全店ぶん見ています。

### 何人態勢の店か

店の規模も違います。`headcountProfile` に最頻値・中央値・四分位・分布を持たせ、店舗チップのツールチップと凡例で使っています。

| 店舗 | 昼 | 夜 |
|---|---|---|
| 1号店 | 6人（36%）・5〜7人が中心 | 6人（44%）・5〜6人 |
| 2号店 | 5人（33%）・5〜7人 | 6人（44%）・6〜7人 |
| 3号店 | 6人（38%）・5〜7人 | 6人（52%）・6〜7人 |
| **4号店** | **4人（58%）・4〜5人** | **4人（61%）・4〜5人** |

**4号店だけ2人少ない体制で固定**されています。1号店の最大13人は生誕祭・周年などのイベント日の外れ値です。

なお、店舗数の判定に使う定員は最頻値ではなく**平均**（`typicalHeadcount`）です。実測で比較したところ平均がいちばん当たりました（昼86.4% / 夜87.5%。中央値は昼86.4% / 夜83.5%、最頻値は昼84.1% / 夜83.5%）。ただし店舗数そのものは、上に書いた `openCountByHeadcount` の実測境界で決めています。`typicalHeadcount` は店舗が決まったあとの人数配分に使います。

また、営業の仕方にも偏りがあります。2〜4号店は片方のシフトだけ開ける日が多数派で（4号店は 84.3%）、昼と夜で開店店舗が違う日が 73% あります。同じ日の中で2号店と3号店が入れ替わった例は 0 件で、入れ替わるのは翌日です（**同日ルールを2・3号店に限っているのはこの実績が根拠です**。ただし「避け合う」こと自体は4号店も同じで、上の「4店の関係」を参照してください）。

**1号店も毎日開いているわけではありません。** 昼は 98.1%、夜は 93.9%（土曜の夜は 90.4%）で、直近180日では夜だけ休みだった日が9日ありました。直近1年では終日休みが2日です。「1号店に行けば必ず開いている」とは考えないでください。

### データの出どころ

[`data/store-insights.js`](data/store-insights.js) は、公式X [@akibazettai](https://x.com/akibazettai) の「ひるにゃんこ / よるにゃんこ」投稿を Wayback Machine 経由で復元した出勤実績から作っています。カレンダーに持たせている実績は直近180日ぶんです。

**集計期間は用途で分けています。**

| 対象 | 期間 | 理由 |
|---|---|---|
| 店舗の営業率・規模・ローテーション・精度 | 直近1年（361日） | 在籍者と無関係なので、長いほうが当たる |
| **メイド個人の店舗傾向** | **直近120日** | 見習いの研修期間が約3か月。1年で集計すると「当時は見習いだった人」を今の在籍として数えてしまう |

期間は `sampleWindow` と `tendencyWindow` に入っています。個人の傾向だけ期間が短いことは、メイドさんのチップのツールチップにも「直近120日」と明記しています。

**店舗側の窓を縮める案は測って却下しました。**「365日は長すぎるのでは、120日では」という問いへの答えです。

| 窓 | 配属から | 実績の傾向から |
|---|---|---|
| 90日 | 42.4% | 43.6% |
| 120日 | 45.8% | 46.6% |
| 180日 | 50.0% | 49.2% |
| **365日** | **50.4%** | **52.5%** |

**短くする理由がありません。**個人の傾向を120日にしているのは在籍が入れ替わるからで、店舗の営業パターンにはその事情がありません。

**この README に書いた的中率は、リポジトリの中だけでは再現できません。** 訓練と評価を時系列で分けて測るため、比較には約2年ぶん（訓練365日＋評価365日）の出勤実績が要りますが、[`tools/data/shifts.csv`](tools/data/shifts.csv) は生成に必要な直近400日ぶんしか持っていません。数値は復元した全期間（2019年以降・34,720行）に対して別途測ったもので、検証用のスクリプトともども収集側の作業ディレクトリにあります。数字を測り直すときはそちらが要ります。

| [`tools/data/openings.csv`](tools/data/openings.csv) | 顔ぶれは分からないが営業した店舗だけ分かっている日。`actual` にのみ反映し、統計には混ぜません |
| [`tools/data/events.csv`](tools/data/events.csv) | 生誕祭・周年・卒業イベント（顔ぶれが変わるため傾向計算から除外） |

生成物はブラウザーが読むだけの静的テーブルです。表示時に重い計算はしません。

#### 店舗だけ分かっている日を足す

`shifts.csv` は公式Xの「ひる/よるにゃんこ」投稿から復元したもので、**誰が出たか**まで分かります。一方、メイドさん個人の当日投稿などから「この日この店が開いていた」とだけ分かることがあります。その場合は `tools/data/openings.csv` に1行足して再生成します。

```csv
"date","shift","stores","source"
"2026-09-02","昼","s1|s2","メイドさんの当日お給仕投稿"
```

人数が分からないため**統計には混ぜません**（母数がずれます）。`shifts.csv` に記録のあるシフトは上書きしません。この経路で入った日は `actualWithoutRoster` にも記録され、カレンダーのツールチップで「営業した店舗だけが分かっていて、誰がいたかの記録はありません」と断ります。表示される顔ぶれは予定表からの割り振りです。

#### 見習いにゃんこの見分け方

**お店は、見習いを終えたメイドさんに X のアカウントを渡します。**そこを線にしています。

| 条件 | 扱い |
|---|---|
| アカウントがある（卒業表記なし・本人の初日より後に作成） | 昇格済み |
| アカウントが無く、初日から `TRAINEE_MAX_DAYS`（90日）以内 | 見習い |
| アカウントが無いまま90日を過ぎた | 昇格せずにいなくなったと見る |
| 初日が `TRAINEE_WINDOW_DAYS`（120日）より前 | **判定しない** |

初日は `debuts.csv` の告知を優先し、無ければ記録上の初出で代用します。

窓を切っているのは、遡るほど**卒業したメイドさんが見習いに見えてくる**ためです。卒業した方も現行のアカウントを持たないので、記録だけでは新人と区別が付きません。窓の外では `actualRoster` に `trainees` キーを置かないので、「判定していない日」と「全員が昇格済みの日」を取り違えずに済みます。

アカウントの有無だけでは足りません。**同じ名前で、卒業した方のアカウントが残っていることがあります。**`ひじり` がそれで、`hijiri_zettai` は2019年作成・プロフィールに卒業表記があり、いまのひじりさんの初日は2026-08-03です。`accounts.csv` の `source` が `卒業済み` のもの、および本人の初日より前に作られたものは、昇格の証拠として数えません。

#### 予測と実績の突き合わせ

実績が届いた日について、**届く前に出していた予測**を [`tools/data/forecast-log.csv`](tools/data/forecast-log.csv) に残しています。カレンダーはこれを読みません。当たり外れを画面に出すためではなく、あとで精度を measure し直すための記録です。

```csv
"date","shift","captured_at","predicted_stores","actual_stores","maid","predicted_store","actual_store","verdict"
```

`verdict` は `hit` / `miss` / `absent`（予定表にいたが投稿に無い）/ `unlisted`（予定表に無いが出ていた）です。**予定表に載っていなかった人は外れに数えません。**予定表に出ないのはお給仕予定を出していない人で、当てられなくて当然だからです。

### 既知の差分

- `data/schedule.js` の `roster` は39名です。うち35名は公式サイトのメイドさん紹介に載っており、4名（`unpostedMaids`）はまだ載っていません。**逆に、サイトに載っているのに `roster` にいない方が1名います**（`まひろ`）。集計期間に1件もお給仕記録が無いため `maidTendency` を作れず、追加すると `validate-insights.js` の照合が落ちます（公式サイト上の詳細ページも `detail___trashed` という削除済みの URL です）。いまは `unlistedMaids` 側で把握しています。記録が出たら `roster` に追加し、`data/store-insights.js` を再生成すれば追従します。
- 所属（`homeStore`）と、実績から推定した最多店（`home`）は4名で食い違います。`える` は所属4号店／実績1号店、`あめる` は3号店／1号店、`みりん` は1号店／4号店、`ゆめ` は2号店／3号店です。前者が所属、後者はヘルプを含めた実態なので、どちらも誤りではありません。
- 公式サイトの在籍一覧に無いものの最近お給仕に出ている方は、**カレンダーには表示していません**。予定表に載らない以上、その日いるかどうかを言えないためです。判定結果は `unlistedMaids` に持っていますが、いまは画面に出していません（下記「在籍・新人の判定について」を参照）。

### お給仕予定の公開方式が変わりました（移行期）

**2026年9月1日から、お給仕予定は上旬・下旬をまとめて事前公開する方式になりました。** それ以前は当日発表で、その日にならないと誰が出るか分かりませんでした。

ノーマル以上は全員が提出しますが、移行直後はまだ提出していない方がいます。カレンダーの下に、この事情を説明する一文を出しています。**この注意書きは `scheduleSystemChangedAt` から60日で自動的に消えます。**

**ただし人数そのものは、思ったほど薄くありません。** 予定表に載るのは `roster` の方だけなので、比べる相手も「実績のうち `roster` の人」でなければいけません。そう揃えるとほぼ一致します。

| | 実績のうち `roster` の人 | 9月の予定表 |
|---|---|---|
| 昼 | 8.5人 | 8.5人 |
| 夜 | 7.4人 | 6.8人 |

実績には見習いとサイト未掲載の方も含まれるので、全員だと昼10.9人・夜9.8人になります。**予定表がこの数字に届かないのは当然で、届かないこと自体は未提出の証拠になりません。** 薄さが出ているのは人数ではなく顔ぶれのほうで、`roster` 39名のうち7名は9月前半に1件も予定がありません。

**この薄さに合わせた補正は入れていません。** 一時的な未提出が原因なので、予定表の人数を基準にすると提出が揃ったあとに過大評価になります。店舗数の判定は `roster` を母数にしているため、揃ったあとも破綻しません。

**見習いだったころの出勤は、その母数に数えません。** 見習いは予定表に載らず、当日のお給仕投稿で初めて分かる存在でした。いま `roster` にいる人でも、昇格前は「事前に分からない人」だったので、そのころの出勤を数えると母数が実際より多く見えます。`promotedAt` に昇格日を持たせ、その日以降だけ数えています。

これは効きます。2026年8月に昇格した4名（`ゆめ`・`にゃな`・`ぴあの`・`もち`）を通年で数えると、閾値がずれます。

| | 昼 | 夜 |
|---|---|---|
| 昇格前も数える | `[5, 13]` | `[5, 14]` |
| **昇格後だけ数える** | `[5, 14]` | `[5, 12]` |

夜で2人ぶんの差で、**13人で3店舗と言うか、15人まで待つか**が変わります。

なお `tools/data/shifts.csv` は公式Xの当日投稿から復元した**実績**です。当日発表時代のものなので「事前に分かる情報」ではなく、予測の学習には使えますが「予定表に何人載るか」の基準にはそのまま使えません。`rosterCoverage.unlistedPerShift`（見習いぶん0.87人）も当日発表時代の値なので、移行が落ち着いたら測り直しが必要です。

### 在籍・新人の判定について

**この節の判定結果は、いま画面に出していません。** かつては凡例の下に一覧として出していましたが、カレンダー下の解説ブロックごと削除しました（冗長なため）。`unlistedMaids` は `data/store-insights.js` に残っており、`validate-insights.js` が形を検証しています。**この方々の名前をカレンダーに出せない理由**（予定表に載らないので、その日いるかどうかを言えない）は変わらないので、判定そのものは維持しています。

`unlistedMaids` の判定は控えめにしています。

- **卒業・離脱**（`status: "graduated"`）は、卒業イベント・2週間以上お給仕が無いこと・Xのプロフィールの卒業表記のいずれかで判断します。
- **`likelyNew`（新人かも）** は、公開アカウントがあり直近1か月にお給仕があることに加えて、**古いアカウントが見つからず、1年より前の出勤記録も無い**場合だけ立てます。復帰時にアカウントを取り直す実例が複数あるため、**アカウントの作成年が新しいことだけを根拠に新人とは判定していません**。古いアカウントは「以前から在籍していた」という一方向の証拠としてのみ使います。
- **ツイートが20件未満のアカウントは、同名の別人（休眠垢）とみなしてリンクしません。** 実際に、いま出ている方とは別人の同名休眠垢が1件ありました。
- `tools/data/shifts.csv` は直近400日ぶんなので、初出の日付はこの範囲で頭打ちになります。

### 画面に出していない測定値

`data/store-insights.js` には、画面に出していないキーもあります。**消していないのは、出典と再現性の記録だから**です。

| キー | 用途 |
|---|---|
| `generatedAt` / `historyRange` / `sampleWindow` / `shiftDataFrom` | いつ・どの範囲で測ったか |
| `accuracy.maidStoreTop1` / `maidStoreTop2` | 4店すべてを候補としたときの的中（この README の記述の裏づけ） |
| `openCountPerShift` / `shiftSplitGivenOpen` / `shiftPattern` | 店舗数・片シフト営業の分布。閾値を決めた根拠 |
| `rosterHeadcountByOpenCount` | 店舗数ごとの `roster` 人数。`openCountByHeadcount` の裏づけ |
| `unlistedMaids` | 上記の判定結果 |
| `rotation.sameDayS4` / `nextDayByDayS4` | 4号店の遷移。同日ルールを2・3号店に限った根拠 |

**画面の文言に数字を焼き込まない**方針なので、表示に使うキーは残らず読んでいます。上の表はいずれも「なぜこの実装なのか」を後から確かめるための材料で、表示用ではありません。

### カレンダーに出ない人がいます

**カレンダーに載るのは在籍メイドさんだけです。見習いにゃんこがいつお給仕に出るかは当日のお給仕投稿まで分からず、事前に知る手段がありません。**

直近90日（2026-06-01〜2026-08-30、344シフト）の実測では、のべ人数の15%が未掲載で、**1シフトあたり平均0.87人（71.2%のシフト）** が表示されていません。つまり、このカレンダーの人数は実際より1人ほど少なく出ます。凡例にも同じ注意を出しており、文言の数値は `rosterCoverage` から読んでいます。

**店舗チップと店舗ごとの見出しにも、その店の見習い事情を出しています。** 平均を小数で見せても伝わらないので、「何割の枠にいたか」で言います。実測の分布は0人29% / 1人58% / 2人11%で、ほぼ0か1だからです。

| | 1シフトあたり | 1人以上いた枠 |
|---|---|---|
| 1号店 | 0.83人 | 69% |
| 2号店 | 1.22人 | 86% |
| 3号店 | 0.95人 | 79% |
| 4号店 | 0.59人 | **57%** |

**4号店だけ、4割以上の枠に見習いがいません。** 「4人態勢の店」という規模の小ささと合わせて読めるよう、人数の説明と同じツールチップに並べています。数値は `rosterCoverage.byStore` から読み、期間も同じキーから出しています。

なお、見習いが何人来るかを当てる試みは**細かくしても改善しません**。店ごと・シフトごと・曜日ごとに分けても、いつでも同じ人数と言った場合（誤差0.598人）から0.578人までしか縮みません。もともと0か1なので当てようがなく、**「何割の枠にいるか」を正直に出すのが上限**です。

`typicalHeadcount`（お給仕投稿ベース＝見習い込み）とカレンダーの表示人数（在籍のみ）は母数が違うため、そのまま比べると1人ほどずれます。

## お給仕情報の更新

表示データは [`data/schedule.js`](data/schedule.js) だけに集約しています。描画処理は [`app.js`](app.js) に分離されているため、通常の予定更新で HTML や JavaScript のロジックを変更する必要はありません。

1. `lastUpdated` を更新します。
2. `schedule` の日付に、`昼` と `夜` の配列を追加・編集します。
3. 記念日・生誕の主役には `featured: true` と、読み上げ・ツールチップ用の `eventLabel` を指定します。
4. メイド服を着ないキッチンにゃんこは `kitchenStaff` に入れます。カレンダーとフィルターに 🍳 が付きます。
5. 在籍が入れ替わったら `roster` と `homeStore` の両方を[公式サイトのメイドさん紹介](https://akibazettai.com/staff/)に合わせます。`roster` の並びは公式の掲載順（ひかりさんが先頭、キッチンにゃんこ5名が末尾）、`homeStore` は各メイドの店舗タブ（`shopNum01`〜`04` が `s1`〜`s4`）です。
6. **見習いを終えたばかりの方は、公式サイトに載る前に予定を出しはじめます。** 予定を出すのはノーマル以上だけなので、提出があること自体が昇格の証拠です。その場合は `roster` に足したうえで、`unpostedMaids` に名前を、`promotedAt` に昇格日を書きます。公式サイトに載ったら `homeStore` に配属を足して、`unpostedMaids` から消してください。
6. `node tests/validate-schedule.js` を実行します。
7. `roster` を変更したときは `py tools/build-insights.py` で `data/store-insights.js` を作り直し、`node tests/validate-insights.js` を実行します。

各シフトの並び順は `roster` の公式順と一致させてください（検証スクリプトが確認します）。カレンダーは予測モードで店舗ごとに見出しを付けてまとめ、**店舗順 → 各店の中は公式の掲載順**で並べます。

初期表示月と日付範囲は、アクセス時の日本時間から自動計算されます。開始日は当日、終了日は当日が1〜15日なら15日、16日以降なら同じ月の末日です。

予定が未確認の日はキーを追加しません。フィルターには `roster` の全員が公式順で表示されるため、予定がないメイドも削除しないでください。

絞り込みで誰も残らなかったシフトは `-`、そもそも公開情報を確認できていないシフトは「確認情報なし」と表示します。

## 公開状態

リポジトリは公開（public）で、GitHub Pages でサイトを公開しています。無料プランの GitHub Pages は公開リポジトリでしか使えないため、非公開にすると Pages も停止します。

`main` への push で [ワークフロー](.github/workflows/deploy-pages.yml)が動き、データ検証に成功した場合だけサイトが更新されます。

HTML、CSS、JavaScript、予定データはリポジトリのプロジェクトパスで動作する相対パスを使用しています。

### 更新がブラウザーに届くまで

`index.html` は読み込むファイルに中身のハッシュを付けています（`app.js?v=6c9e3ac864`）。`tools/build-insights.py` が書き込み、`tests/validate-schedule.js` が照合します。手で `app.js` や `styles.css` を直したあと再生成を忘れると、そこで落ちます。

これは**新しい `index.html` が古い `app.js` と組になる**のを防ぐためのものです。付ける前は、データを更新しても画面に予測が出たままになりました。

**`index.html` 自体には付けられません。** GitHub Pages は `Cache-Control: max-age=600` を返すので、**デプロイ後10分は、一度開いたブラウザーに古い `index.html` が出ます**。古い `index.html` は古いハッシュを配るので、資産も古いままです。10分で自然に解消します。

**デプロイ直後に本番を確かめるときは、`index.html` にキャッシュ避けを付けてください。**

```
https://agurakakenai.github.io/akibazettai-schedule-calendar/?fresh=1
```

これを付けずに「反映されていない」と判断した例が、開発中に2回あります（1回は本当にキャッシュ、1回は正しい実装をバグと誤認しかけた）。

### 非公開に戻す場合

1. リポジトリを private にすると、GitHub Pages は自動的に停止します（サイトは 404 になります）。
2. その状態で push すると deploy ジョブが失敗するため、deploy ジョブに `if: github.event_name == 'workflow_dispatch'` を付けて手動実行専用にします。
3. 閲覧は [`preview.cmd`](preview.cmd) でのローカルプレビューに切り替えます。

### 自分だけが見られる形で公開したい場合

| 方法 | リポジトリ | サイト | 費用 |
|---|---|---|---|
| GitHub Pages（無料プラン） | 公開が必須 | 誰でも閲覧可 | 無料 |
| GitHub Pages（Pro） | 非公開にできる | **URL を知っていれば誰でも閲覧可** | 月 $4 |
| Azure Static Web Apps | 非公開のまま | **許可した本人だけ** | 無料枠 |
| Cloudflare Tunnel + Access | 非公開のまま | 許可した本人だけ | 無料（独自ドメインが必要） |

GitHub Pages は Pro にしてもサイト自体は公開されます。サイトを本人だけに限定できるのは GitHub Enterprise Cloud だけです。

[`staticwebapp.config.json`](staticwebapp.config.json) には Azure Static Web Apps 用の設定を用意済みです。全ページを `schedule-reader` ロールに限定し、未認証のアクセスは GitHub ログインへリダイレクト、ロールがないアカウントには [`unauthorized.html`](unauthorized.html) を返します。

#### Azure Static Web Apps で非公開のまま閲覧できるようにする手順

1. [Azure Portal](https://portal.azure.com/) で「静的 Web アプリ」を作成し、プランは **Free** を選びます。
2. デプロイソースに GitHub を選び、このリポジトリと `main` ブランチを指定します。
3. ビルドのプリセットは「カスタム」、アプリの場所は `/`、API の場所は空、出力先は `/` にします（ビルド不要のため）。
4. 作成すると `.github/workflows/azure-static-web-apps-*.yml` が自動で追加され、以降は push でデプロイされます。
5. リソースの **設定 → ロールの管理 → 招待** を開きます。
   - 承認プロバイダー: **GitHub**
   - 招待するユーザー: 自分の GitHub **ユーザー名**（Entra ID を選んだ場合はメールアドレス）
   - ロール: `schedule-reader`
   - 有効期限: 最大 168 時間（7日）
6. 生成された招待リンクを自分で開き、GitHub でサインインします。**リンクを開いて初めてロールが付与されます。**

これで、サイトの URL にアクセスできるのはロールを付与したアカウントだけになります。ロールのないアカウントがサインインしても [`unauthorized.html`](unauthorized.html) が返るだけです。リポジトリは非公開のままで構いません。

補足:

- 事前構成済みのログイン方法は **GitHub と Microsoft Entra ID** で、Free プランでも追加設定なしに使えます。Google などを足す場合は Standard プランが必要です。
- 招待によるロール付与は全プランで使えます。Standard 限定なのは「関数でロールを自動割り当てする」機能だけです。
- Free プランの上限は帯域 100 GB/月・アプリサイズ 250 MB・カスタムドメイン 2 件で、このサイトの規模なら十分です。
- アクセスを取り消したいときは、同じ「ロールの管理」からユーザーを削除します。
