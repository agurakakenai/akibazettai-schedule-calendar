# アキバ絶対領域 お給仕カレンダー

アキバ絶対領域の公開情報を、**イベント画像が見える7列の月間カレンダー**で閲覧する静的サイトです。既定モードは `calendar`、初期範囲はアクセス時の日本時間（JST）の当月全日です。日付をクリック、またはフォーカスして Enter / Space を押すと、昼・夜を区切った詳細が開きます。

公開サイト: <https://agurakakenai.github.io/akibazettai-schedule-calendar/>

## ローカルプレビュー

依存パッケージやビルドは不要です。[`preview.cmd`](preview.cmd) をダブルクリックし、ブラウザーで <http://localhost:4173> を開いてください。

コマンドで起動する場合は、リポジトリのルートで次を実行します。

```powershell
py -m http.server 4173 --bind 127.0.0.1
```

`--bind 127.0.0.1` を付けているため、同じネットワークの他の端末からは見えません。

> Windows で `python` がマイクロソフトストアのスタブになっていることがあります。その場合は `py` を使ってください。

データ検証:

```powershell
node tests/validate-schedule.js
node tests/date-defaults.js
node tests/range-rendering.js
node tests/month-calendar.js
node tests/observed-shifts.js
node tests/validate-insights.js
node tests/store-outlook.js
node tests/headless-render.js
py -B -X utf8 tests/test-insights-tools.py
py -B -X utf8 tools/check-readme.py
py -B -X utf8 -m unittest discover -s tools\tests -p "test_*.py"
```

`validate-insights.js` は [`data/store-insights.js`](data/store-insights.js) の形（店舗ID・確率の範囲・`roster` との一致など）を、`store-outlook.js` は `app.js` の「実績 / 翌日見込み / 同日の実績 / 曜日傾向」を選ぶロジックを検証します。`headless-render.js` は最小の DOM シムで実際に描画し、ランタイムエラーやバッジ・チップの中身を確認します（依存パッケージは不要です）。**月間表示と従来の3モードを描き、「店舗別一覧」と「この人はどこ」が同じ人・同じ日に同じ店・根拠を出すことも突き合わせます。**

`month-calendar.js` は月間表示のロジックを検査します。Chromeによるブラウザー検証は任意です。**Node.js 22以降の組込機能とCDPを使い、依存パッケージは追加しません**。Chromeの実行ファイルを `CHROME_PATH` で指定し、画像出力ディレクトリを渡します。

```powershell
$env:CHROME_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
node tests\browser-calendar.js .\browser-artifacts
```

専用profileのヘッドレスChromeで1280 / 390 / 320幅と、popupの実績・予測を検証します。普段使用しているブラウザーprofileは使いません。

## イベント画像と日付の詳細

月間表示は日曜始まりの7列で、イベントを**昼夜で二重にせず1日単位**で見せます。`schedule[日付][昼/夜]` の `featured: true` と `eventLabel` から主役とラベルをまとめ、`insights.maidTendency` の `alias` で同じ主役の重複を除きます。**日付に画像があることは、昼夜両方のお給仕を意味しません。**クリック / Enter / Space で詳細を開き、昼と夜の記録・予定・店舗見込みを区別して確認してください。

月移動や「今月」では、通常は表示範囲も対象月の1日〜末日に合わせます。**手動指定した `customRange` は維持**し、期間外の日付は無効セルになります。期間外のイベント画像や詳細は表示しません。

配色は**常にライトテーマ**です。OSのダーク設定や旧 `scoutTheme` パラメータでは切り替えません。`color-scheme: only light` と同名のmeta指定で、フォーム・日付入力・スクロールバーにもライト配色を指定し、ブラウザーのAuto Dark変換を抑止します。アクセシビリティの `forced-colors` は無効化していません。

詳細popupの上部にある**「昼へ」「夜へ」**で、各時間帯の見出しへ移動できます。昼夜を切り替えて片方を隠す操作ではなく、**両方の名簿が同じスクロール内に常に表示**されます。ジャンプボタンと「閉じる」は固定領域にあり、スクロール中も利用できます。

画像設定は `data/schedule.js` の `eventImages` です。優先順位は**日付＋主役 → 人物 → 共通fallback → `assets/events/flower.svg`**。画像を設定しただけではイベントや出勤予定は追加されません。`milestones` の入店日からも、イベントや出勤は自動生成しません。

1. 使用する画像を `assets/events/` 等へ置き、画像を説明する `alt` を用意します。
2. 人物共通の画像は `maids[名前]`、特定日の上書きは `events[日付][名前]` に `{ src, alt }` を設定します。
3. 対象日の主役・出勤時間帯は、画像とは別に `schedule` の `featured` / `eventLabel` と昼夜の予定で管理します。

```javascript
eventImages: {
  fallback: { src: "assets/events/flower.svg", alt: "イベント用の花の仮イラスト" },
  maids: {
    "ちま": { src: "assets/events/chima.svg", alt: "ちまのイベント用の仮イラスト" }
  },
  events: {
    "2026-09-03": {
      "ちま": { src: "assets/events/chima.svg", alt: "この日のイベント用の仮イラスト" }
    }
  }
}
```

`src` は画像のパス、`alt` はその画像の説明です。同梱の `monaka.svg` / `chima.svg` / `arata.svg` / `akubi.svg` / `flower.svg` は**独自制作の仮イラスト**で、ご本人の写真や確認済みの好みを表すものではありません。画像の読込に失敗した場合は内蔵の花へ、それも失敗した場合は画像を隠して名前とイベント名を残します。

## 店舗の見込み表示

まず月間カレンダーでイベントを見て、日付の詳細で昼・夜の情報を確認できます。**従来の3モード、期間指定、人物の絞り込みも補助機能として残しています。**モードの保存先は `akibazettai:view-mode:v2` に移行しました。旧キーの選択は引き継がず初回は月間表示になり、その後のV2での選択はブラウザーに記憶されます。

| モード | 内容 |
|---|---|
| 店舗別一覧（`forecast`） | 開いていそうな店舗と、その日出るメンバーの割り振りを出します。メイドさんは予測した店舗順に並びます |
| お給仕一覧（`roster`） | 店舗の予測をすべて隠し、誰がお給仕に出るかだけを見ます。並びは `roster` の公式順です |
| この人はどこ（`maid`） | メイドさん1人ずつに、その月どこに立ちそうかを日付順で並べます（人 → 日付 → 店） |
メイドの絞り込みには「**キッチンにゃんこを除く**」チェックがあります。チェックすると `kitchenStaff` の5名をカレンダーから隠します（店舗の見込みと割り振りは変わりません。裏側では全員で計算しています）。リセットで解除されます。

日付の詳細や店舗別一覧の昼・夜それぞれに、その時間帯にどの店舗が開いていたか（開きそうか）を表示します。バッジは4種類で、次の優先順位で採用します。予測同士の確度がこの順に高いことを保証するものではありません。

| バッジ | 意味 |
|---|---|
| 実績 | 公式Xの投稿で確認できた、その日そのシフトの営業店舗 |
| 翌日見込み | 前日の同じシフトの実績から、ローテーションで見積もった値 |
| 同日の実績 | **同じ日のもう片方のシフト**の実績から見積もった値 |
| 曜日傾向 | 曜日ごとの過去1年の営業率。その日の予測ではありません |

見込みは**記録の最終日以降にしか出しません**。過ぎた日にたまたま記録が無いのは「休みだった」ではなく「記録が無いだけ」なので、そう断ります。記録は昼だけ・夜だけ入ることがあるため、判定は日ではなくシフト単位で行います（例: 昼だけ記録のある日の翌日は、昼が見込み・夜が曜日傾向になります）。

### 記録のある日は、記録の顔ぶれを出します

**人物の実績があるシフトでは**、`insights.actualRoster` の「誰がどの店にいたか」をそのまま出します。**店舗の実績だけがある場合は別です。**`actualWithoutRoster` は営業店舗しか確定しません。顔ぶれを予定表から割り振ることはありますが、その人物を「いた記録がある」「確定」とは表示しません。

**人物名簿のあるシフトの顔ぶれは記録から決めます。**予定表に名前があっても、その記録に無ければ出しません（記録に無いことだけで欠勤理由までは断定しません）。逆に、記録にしかいない方も出します。

並びは公式の掲載順のままです。**`roster` に無い方は、その後ろに記録の並びで置きます。**この方たちにはメイド絞り込みのチェックボックスがないので、**絞り込みを始めた時点で隠します**（＝全員選択のときだけ出ます）。チェックボックスの無い名前が絞り込みをすり抜けると、「1人だけ選んだのに他の名前が出る」ことになるためです。

人物の配属記録がある行には**確率を出しません**。`title` は「◯号店にいた記録があります」になります。店舗だけの実績から、この文言を作ってはいけません。

### 見習いにゃんこには 🔰 を付けます

`actualRoster` の `trainees` にいる方に 🔰 を添えます。絵文字だけに頼らないよう、行は破線の枠（`.is-trainee`）にし、`title` と `aria-label` に「見習いにゃんこ」と書きます。🔰 自体は `aria-hidden` で、読み上げは行のラベルが担います。

**手動実績の `actualRoster` に `trainees` キーが無いシフトでは、誰にも印を付けません。**直近120日より前は判定していないためで、これは「全員が昇格済み」ではなく「**分からない**」です。実装でも `?? []` で潰さず、キーの有無で分けています。自動観測の印には、下記の `traineePeriods` を使います。判定の中身は[見習いにゃんこの見分け方](#見習いにゃんこの見分け方)にあります。

### まだ予定を出していない方がいることを言います

在籍40名のうち8名が現在の予定表に掲載されていません。画面では「未提出」と案内しますが、提出手続き自体を観測したわけではなく、予定が一度も無いことによる判定です。見習い・歴史的な未掲載とは別集団です。以下の人数比較だけで欠員の理由がすべて分かるわけではありません。

```
予定表 8.3人 + 未提出ぶん 1.8人 = 10.1人   記録 9.85人
```

カレンダーの下に1行出します。詳細（誰が未提出か・最近の出番）はツールチップと読み上げに入ります。

> 在籍40名のうち8名が、まだ予定を出していません

**推定で埋めません。**誰が抜けているかは分かりますが、その人が今月何日出るかは分からず、提出が進むぶん補正を減らす仕組みも要ります。**「揃っていない」と言うほうが、揃えば自動で黙る**点でも正しい形です。`schedulePending.pending` が空になれば消えます。

**「何人ぶん薄いか」は `schedulePending.windowShifts` で割って出します。**分母がデータに入っているので推測になりません（328回 ÷ 177シフト ＝ 1.9人）。**入っていなければ書きません。**推測した分母で割った数字は、測った数字の顔をしてしまいます。テストは「印字した値が `windowShifts` から出たものと一致すること」を見ているので、別の窓で割ると落ちます。

既存の[制度変更の注意書き](#店舗の見込み表示)は「出していない人がいることがある」までしか言えず、日数で自動的に引退します。こちらは**実際に誰が出していないかを見て**出るので、両方が並びます。

### 開く店の数が表の上限に当たったら、そう断ります

店舗数は `openCountByHeadcount` を引いて決めています。この表は「何人を超えたら1店増えるか」の区切りなので、**言える最大は要素数+1**です。いまは2要素なので3店までしか答えられません。

3要素目が無いのは、**4店のシフトがほとんど無い**からです。2026-09-03の昼にはじめて起きて、787シフト中1件です。

```
1店  186 シフト (23.6%)
2店  563 シフト (71.5%)
3店   37 シフト ( 4.7%)
4店    1 シフト ( 0.1%)   ← 2026-09-03 昼
```

そのままだと画面には「3店」としか出ず、**3店が最有力だと読まれます**。そこで**予測した店舗数が上限と等しいとき**に断りを出します。

```
1号店   3号店   4号店
3店までしか数えられません
```

ツールチップと読み上げには理由まで入れます。

> この昼は3店で、いまの表で言える上限です。3店より多いシフトは昼360件の記録に1件しかありません。**3店がいちばんありそう、という意味ではなく**、これより多いかどうかを数える材料がありません

**上限も件数も表から引きます。**`openCountByHeadcount` の要素数と `openCountPerShift` の分布で決まるので、記録が増えれば文言も追随します。テストも同じ引き方をするので、数字を書くと落ちます。**この「1件」は 2026-09-03 の昼で、それまでは0件でした。**

記録のあるシフトには出しません（実際に何店開いたか分かっています）。上限が全店に届いている場合も出しません（それ以上の店が存在しないので、数えられないものがありません）。

**閾値 `[5, 12]` は維持しています。**2026-09-03までの全787シフトを、本番の `listed_on` / `promotion_dates` による**キッチン込みのユニーク人数**で比較しました。

| 表 | 店舗数の的中 | 4店と言った回数 | うち当たり |
|---|---|---|---|
| `[5, 12]`（現行） | **701/787 = 89.1%** | 0回 | 0回 |
| `[5, 12, 15]` | 697/787 = 88.6% | 7回 | 1回 |

増設は4店の見逃しを1件減らし、**4店誤報を6件増やします**。そのうち1件は旧方式も店舗数を外すため、完全一致の対比較は**1勝5敗、4/787 = 0.508ポイント低下**です。旧説明の「10誤報・0.7pt」は明記された昇格日だけを使う別の人数定義でした。

- 店舗数完全一致を同じ価値で評価するなら現行維持。
- 新しく当たる4店の価値が他の正解の**5倍を超える**なら、重み付き完全一致では増設が有利。
- 4店検知の FP/FN だけを評価するなら、見逃し損失が誤報の**6倍を超える**と増設が有利。

これは当時の事前予定表ではなく、実績から「掲載されるはずの人」を復元した**歴史的proxy**です。未提出や欠勤は復元できず、同じ固定閾値を全履歴で評価しています。4店実績1件への最適化を将来性能とは扱いません。[再現手順](#評価の再現と限界)で数え直せます。

### 店ごとに独立して判定する案

「4店舗を独立に集計すれば上限が消えるのでは」という案も測りました。**1店ずつの精度は保たれますが、店舗数が壊れます。**

| 方式 | 組が一致 | 店ごと | 店舗数 |
|---|---|---|---|
| 現行（人数→上位N店） | **48.3%** | 76.1% | **88.1%** |
| 独立（曜日・人数・前日） | 36.4% | 74.9% | 64.0% |
| 独立＋配属者の人数 | 39.0% | **76.5%** | 61.9% |
| 独立＋配属者の人数と割合 | 34.7% | 74.6% | 58.9% |

**現行方式の強さは「何店開くか」を88.1%で当てているところ**にあります。独立に切ると「だいたい2店」という制約が使えなくなり、店舗数が62%まで落ちます。顔ぶれの配属を足すと「店ごと」は現行を上回りますが（76.5%）、店舗数は戻りません。

独立方式は閾値を下げれば4店を出せますが、**9/3の昼を流しても4店になりません**（`s1 98% / s2 30% / s3 32% / s4 22%`。4号店は前日開いていて配属者も3人いるのに22%）。**その日は実際に4店とも開きました。** どの方式でも、いまある記録からは当てられない日でした。


### 昼の記録から、夜の行き先を読み直します

2026-09-03を終端とする本番の365日窓では、**昼夜とも出た1129人回のうち793人回（70.2%）が別の店**にいました。これは人のユニーク数ではなく、日付×人物の通し勤務回数です。全履歴なら1241人回中852人回（68.7%）で、同じ母集団ではありません。

正確な分母・移動人数は `sameDayMaidMoveSummary.personPairs` / `movedPersonPairs` に持ちます。期間は同じキーの `from` / `to`、単位は `date-person` です。割合はこの整数から計算し、丸め済みの遷移確率を人数へ逆算しません。README検査は、この節の人数・移動人数・移動率をまとめて照合します。

`insights.sameDayMaidMove`（全体）と `maidTendency[名前].sameDayMove`（人ごと・40名中25名）を使い、**その人の傾向に移り先の確率を掛けます**。

```
score(店) = その人の夜の傾向(店) × 移り先の確率(昼の店 → 店)
```

**置き換えず、掛けます。**置き換えると「夜はみんな1号店」になって、その人の癖が消えます。掛けた結果が全滅したとき（その店に移った記録が1件も無い場合）は傾向だけに戻します。**移り先が読めないことと、行かないことは違います。**

**昼に人物の実績があるときだけ使います。**昼が見込みだと推測の誤差が夜にも乗るためです。夜に人物の実績があれば割り振りは不要です。

旧記述の **62.2% → 69.0%** は、移動の学習も120日、実際に夜に開いた店を知る oracle 条件、個人独立 argmax、平滑化ありの**別実験**でした。同条件の現データ580人回では傾向のみ62.2%、平滑化69.0%、ゼロ落とし＋全滅時 fallback 68.4%。1店舗の夜も含めると661人回で66.9% / 72.8% / 72.3%です。

本番は移動365日・傾向120日、ゼロ＋fallback に加え、店舗予測、整数定員、キッチン優先、縮約・公式配属 prior・イベント除外を含みます。時間分離した本番フロア通し勤務352人回の対照は、補正なし186/352（52.8%）→あり190/352（54.0%）、34勝30敗です。580人回の置換値でも、将来精度の保証でもありません。補正は削除していません。

移り先を使った行には、**推測に使った手がかりも書きます**。昼の店から夜の店への移動表は過去実績であり、その人が今回移動する理由や、夜の確定情報ではありません。

### キッチンにゃんこは、見込みの日には店を名乗りません
見込みのシフトでは、キッチンにゃんこを店ごとの一覧から外し、専用の見出しの下に置きます。**名前は出します**（予定表に載るので、誰が出るかは分かります）。分からないのは、どの店にいるかです。

理由は2つあります。

**当てられません。** 実測の確度はフロア65.4%に対しキッチン58.7%です（うる52% / みりん55% / まこっちゃん61% / けだま62% / あらた65%）。

**当てる必要もありません。** 開いた店の枠にキッチンが載っているのは90%（1号店83% / 2号店99% / 3号店100% / 4号店95%）で、1店なら1人・2店なら2人と各店1人ずつです。「どの店にいるか」は「どの店が開くか」とほとんど同じことしか言っていません。掛け持ちは1470件中16件だけです。

**店舗チップも出しません。**「店を名乗らない」と決めた以上、チップで名乗ると見出しと矛盾します。

**人物の実績があるシフトと、記念日の主役の予定は別に扱います。**前者は実際の配属記録、後者はイベント主役としての予定です。通常のキッチン配属の推測とは分け、予定を過去の実績とは表示しません。

**店舗数の計算からは外しません。**キッチン人数だけで店舗数を当てると80.9%、総人数なら92.9%です。総人数に入れたままがいちばん当たります。

**`roster` からは外しません。**公式サイトは5名とも「メイドさん紹介」に載せていて（各店の掲載の末尾）、予定表にも出ます。フロアかキッチンかを持つのは `kitchenStaff` の役目で、`roster` は「お給仕する方の一覧」です。外すと `maidTendency` との照合が崩れ、カレンダーにも出せなくなります。

代わりに、**分かる形で区別します**。`roster` の並びは末尾5名がキッチン、絞り込みの一覧は `is-kitchen` と 🍳（`aria-label="キッチンにゃんこ"`）付きです。「キッチンに追記しただけで、キャストの側から消えていない」と読まれたので、**この区別が消えたら落ちる検査**を足しました。壊し方を5通り試しています（🍳 を外す・読み上げを外す・印ごと外す・全員に付ける・名前の前に置く）。

並びは**店ごとの一覧 → 見習い → キッチン**です。これは確度の順位ではありません。見習いは存在と人数も推測、キッチンは予定上の名前が分かり配属先が不明、という異なる不確かさを分けています。

### 見込みのシフトにも見習いにゃんこを数えます

**見習いは予定表に名前が出ません。**そのままだと、まだ記録の無いシフトは実際より人数が少なく出ます。`insights.traineeOutlook` の「1店あたりの人数」に、開くと見込んだ店の数を掛けて丸めた人数を足します。

| 開く店 | 昼 | 夜 |
|---|---|---|
| 1店 | 0人 | 0人 |
| 2店 | 1人 | 1人 |
| 3店 | 1人 | 1人 |
| 4店 | 2人 | 2人 |

**名前は出しません。**誰なのかが分からないので「**見習い🔰**」と書き、読み上げにも「どなたかは分かりません」と入れます。同じ表示が複数並ぶことがあります。

**どの店かは「当てられません」と言います。**店の見出しの下に置くと「その店にいる」と読まれるので、**店を名乗らない一覧として置きます**（`.maid-trainee-list`。`.maid-list` は「見出しと1対1」を保つ約束があるので混ぜません）。枠は点線にして、実在の記録より弱く見せます。

**そのうえで、見出しを必ず付けます。**クラスを分けるだけでは足りませんでした。見出しが無いと直前の店の `<ul>` にそのまま続いて見え、店は s1→s4 の順に並ぶので、**`見習い🔰` はいつも番号のいちばん大きい店にぶら下がって読めます**。

**さらに、見出しに開く店を全部書きます。**見出しを足しただけでも足りませんでした。この一覧はかならず店の一覧の後ろに来るので、**文字が店について何も言わないかぎり、位置だけが答えになります**。

```
直す前                    見出しだけ             いま
  4号店   3人              4号店   3人            1号店   6人
    える かなた るるか        える かなた るるか       …
    見習い🔰  ← 4号店に      見習い 1人ほど         3号店   4人
                見えていた      見習い🔰              …
                                                 見習い 1人ほど
                                                 1号・3号 どちらか当てられません
                                                   見習い🔰
```

指摘は2段階でした。「**見習いが絶対に1号店に来ないような見た目**」、そして「**どこかにいるのはそうで、問題はどこにいそうか**」。

**特定店への断定配置はしません。**ただし「どんな方法もランダムに勝てない」という一般的な不可能性は示せていません。[現在の比較条件](#どの店に入るかは断定しません)を参照してください。並べるのは予測で選んだ店であり、実際の見習いのいる店が候補から漏れることもあります。

**「同じくらい」とは書きません。**`traineeOutlook[shift].byStore` は120日内・シフト別・半減期30日の平均人数です。昼は `s1 0.482 / s2 0.503 / s3 0.322 / s4 0.243`。店ごとに異なり、**平均が1未満でも「いない方が確からしい」とは限りません**。存在率でも割り振りの的中率でもありません。

> **「当てられない」と「同じくらい」は別のことです。**前者はこちら側の話、後者は店についての主張で、後者は表が否定します。

これは人ごとの的中率で「この方は読めません」ではなく「**私たちが当てられませんでした**」と書いているのと同じ線引きです。**自分で決めた線を、自分の実装で踏みました。**テストは「同じくらい」「横並び」と書いたら落ちます。

実装の途中で `byStore` を開く店のぶんだけで割り直し、`1号 60%・3号 40%` と出すところまで作りました。**出す前に測って取り下げています。**測り方も一度間違えました（自前の見習い判定が出荷データより広く、0.75 対 0.48 の別集団でした）。作り直した表を出荷値と突き合わせて気づいたので、**検算のほうが先に効きました**。テストは、この見出しに割合が出たら落ちるようにしてあります。

旧画面では最後の店にぶら下がって見えました。昼夜をプールした9種類の窓の比較では、現データで1号店が9/9回最多、4号店が9/9回最少でしたが、これは本番のシフト別120日＋半減期表とは別条件です。9/3の記録でも見習い3名のうち2名は最後の店でなく、1名は先頭の1号店でした。この1日の配置だけで一般的な予測不能性は言えません。

見出しはキッチンと同じ箱にして、**枠線だけ点線**にします（店の見出しは実線）。人数は「**1人ほど**」と書きます。キッチンは予定表から数えた実数ですが、こちらは実績から見込んだ数なので、同じ書き方にはしません。キッチンにゃんこの見出しにも同じ形で開く店を並べます。

以前ここには「1店あたりの実測は1号店0.35 / 2号店0.35 / 3号店0.32と横並びで、どこかを選ぶ根拠がありません」と書いていました。**測り直すと横並びではありません。**理由が違っていただけで結論は同じでしたが、**理由のほうが腐っていました**。

**人物の配属記録があるシフトには出しません。**誰がいたか分かっているところに推測を混ぜる理由がありません。

**見習い見出しに配属確率は出しません。**見習い人数は120日内・半減期30日で見ています（店舗数閾値の半減期180日とは別）。平均人数を割り直すだけでは配属確率にも較正済みの予測にもなりません。テストは、この見出しに `%` が出たら落ちます。

壊し方を試して落ちることを確認しています（見出しを外す・店を名乗らせる・店の見出しクラスを使い回す・人数を実数のように書く・断りを外す・開いている店を落とす・割合を出す）。

なお**匿名で補った見習い人数は店舗数の判断に入れません**。閾値 `openCountByHeadcount` は `listed_on` の掲載対象proxy人数で作っており、🔰の判定と同一ではありません。見習いの予測人数は店舗数から出すので、それを店舗数の入力に戻すと循環します。

**既定の表示範囲はJST当月の1日から末日まで**なので、同じ月の過去の記録も見られます。期間指定は補助機能として残しています。

**同じ数字でも、根拠の重みは違います。** 「翌日見込み」は前日の実績を踏まえた値で、本文にその日付を名指しします。「曜日傾向」は前日が分からないときの値で、本文に「前日の実績が手元にないので」と書きます。**いま予定表に出る30シフトのうち、前日の実績があるのは2件だけ**です。記録は手入力した日しか増えないので、1日ぶん実績が分かると**その翌日1日だけ**が良くなります。

**「同日の実績」は2・3号店にだけ使います。** 昼に2号店が開いていれば夜も2号店で、3号店に入れ替わることはほぼありません（`rotation.sameDay.s2.s3` は該当0件）。ところが曜日傾向にはこの情報がなく、2号店と3号店がどちらも3割前後で並びます。実測で、夜の店舗の組み合わせを丸ごと当てる的中が **23.8% → 30.4%**、2号店の F1 が **5.7% → 39.6%** に上がりました（n=349、McNemar p=0.015）。

#### 前日の夜と、その日の昼は、両方使います

**「2つ前」と「直前」は別のことを言っています。**

| 手がかり | 何を見ているか |
|---|---|
| 2つ前（前日の同じシフト） | 同じシフトどうしの比較。日をまたぐ入れ替わり |
| 直前（同じ日のもう片方） | 同じ日の中の結びつき。2号店と3号店は日中に入れ替わらない |

以前は**前者が取れた時点で後者を捨てていました**。記録のある夜170件のうち、両方が取れるのが170件すべてで、毎回そこで直前を捨てていたことになります。

いまは**掛け合わせます**。対数オッズで足し、素の営業率で割って「その手がかりがどれだけ動かしたか」だけを取り出します。

```
2026-09-02 夜（昼の実績は 1号店・2号店・4号店）
  2号店  23% -> 40%
  3号店  24% ->  1%   ← 昼が2号店なので、夜に3号店へ入れ替わることはほぼ無い
```

#### 過去測定: 固定出荷表による同日補正

以下は方式を選んだ当時の値です。`expectedOpenStores` で採点しましたが、**評価対象の夜の actual だけを消し、未来も含む出荷済み rotation・baseOpenRate・閾値を固定**していました。顔ぶれ補正 `applyHomeStaff` / `applyPostedTilt` も通していません。out-of-sample の本番精度ではありません。

| 方式 | 的中 |
|---|---|
| 2つ前だけ（以前） | 40.6% |
| 直前で上書き | 47.6% |
| 平均 | 51.2% |
| **掛け合わせ（現行）** | **52.4%** |

当時は37勝17敗・p=0.009（170件）。この選択済みデータのp値を将来性能の保証にはしません。掛け合わせの計算自体は既存テストで検査します。

#### 時間分離した同日補正の対照

2026-09-03までのデータで再現した値です。**170件と171件は人数入力・顔ぶれ補正・対象条件が違うため混ぜません。**

| 条件 | 件数 | 補正なし → あり | 対比較 |
|---|---:|---|---|
| 旧条件・固定出荷表（未来を含む） | 170 | 66/170（38.8%）→85/170（50.0%） | 36勝17敗 |
| 同じ170件・同じ旧人数入力、各時点で再生成 | 170 | 61/170（35.9%）→78/170（45.9%） | 29勝12敗、p=0.0115 |
| 本番の推定昇格日人数＋顔ぶれ補正、各時点で再生成 | 171 | 80/171（46.8%）→95/171（55.6%） | 22勝7敗、p=0.00813 |

昼の評価は前日まで、夜は同日昼までの **shifts と openings の両方**で本番 `build()` を呼び、対象の `actual` / `actualRoster` / `actualWithoutRoster` が無いことをassertします。改善方向は残ったので本番補正は維持します。名簿等を固定した歴史的proxy、日間相関、方式選択済みという制限は残ります。

対象は2・3号店だけ、向きは「早いシフト → 遅いシフト」だけです。**この規則が効くのは、昼の投稿が出てから夜が始まるまでの時間帯**で、読み手がいちばん見ている頃と重なります。

1号店と4号店は曜日傾向のままです。4店すべてに同日ルールを当てると、4号店の F1 が 51.2% → 46.3% と落ちます。4号店は片シフトだけの営業が84%で、昼に開いていたら夜は閉まる傾向があるのですが、その効きが強すぎて、夜だけ開く日を取りこぼすためです。

**このルールは「昼の実績 → 夜の見込み」の向きにしか使いません。** `rotation.sameDay` はその向きに作られた表で、逆に当てると別の分布になります。記録176日で見ると、夜が2号店だった日の昼は2号店が58%ですが、この表を流用すると40%と出ます。夜だけ記録のある日（稀です）は曜日傾向に落とします。

なお記録の最終日で欠けているシフトには、「記録だけが手元にありません」と書きません。取りこぼしたのではなく**まだ来ていない**ためです（今日の昼が入った時点で、夜はこの見込みに切り替わります）。

### 表に出すのは店の名前だけです

**開くと見込んだ店のバッジだけを出し、表面には確率を表示しません。**店ごとの見込みは単純に足せず、「52%と42%を足して94%」とは読めません。店側の決定時刻や未公開予定が分かるわけでもありません。

- **バッジが出るのは、開くと見込んだ店だけ**です。その店に顔ぶれを割り振ります
- 僅差で選ばれなかった店は「**かも**」を付けて、破線の枠で出します。これは予測候補の不確かさであり、店側がまだ決めていないことの証拠ではありません
- **数字は HTML に残しています。** 4店ぶんの割合・根拠・較正・母数は、ツールチップと読み上げ用テキスト（`.visually-hidden`）にすべて入っています

メイドさんの行にも割合は出しません。店舗ごとの見出しがその店を名乗っているので、行に繰り返す意味がないためです。見出しと違う店に割り振られた人だけチップが付きます。行の `title` には、その人の全店の確率と根拠が入ります。

### 「この人はどこ」モードの注意

**日付は行ごとに書きます。**日付を見出しにして昼・夜を束ねる形も試しましたが、**片シフトだけの日が83%**（223件中190日、通しは33日）なので、ほとんどの見出しが1件しか抱えません。入れ子が増えるだけで、読み手には同じことしか伝わりませんでした。曜日はカレンダーと同じ書き方で添えます（「9/3」だけでは何曜日か分かりません）。

```
あむ  12件
  9/3(木) 昼   3号店
  9/3(木) 夜   3号店
  9/4(金) 夜   1号店
```

人物一覧では、**実績・イベント主役の予定・予定からの店舗推測を可視ラベルで区別**します。冒頭の注記も3種類の件数を別々に数え、イベント予定を実績に足して「確定件数」とは書きません。

`maidTendency[名前].accuracy` の `{ rate, n }` は、直近180日の各評価日 d に対し `[d-120日,d)` だけで傾向を作る値です。**実際に2店以上開いた集合を既知とするoracle条件の個人独立argmax**で、本番の店舗予測・整数定員・同日移動・prior込みの的中率ではありません。

> 開店集合を知る条件付き検算の的中率を参考表示します。本番画面の将来精度ではありません。

`p^n` を併記する場合も、各回が**独立で同じ成功確率p**という仮定上の参考値です。同じ日の配置や店舗予測の誤差には相関があり、「6件すべて当たる確率」を実測したものではありません。

- **人によって39%〜81%と幅があります。**全体値（65.6%）で代用すると、当てにくい方を実際より当たるように、当てやすい方を実際より当たらないように書くことになります
- **母数（`n`）も出します。**36件で81%と148件で76%は、同じ確からしさの主張ではありません
- **測れていない方には、全体値で埋めません。**記録が20件に満たない方が1名います。その方には「測れていません」と書きます
- 人物の実績とイベント主役の予定は、通常の店舗推測についての参考計算から外し、それぞれ別件数で表示します

**主語はこちら側に置きます。**「この方は読めません」ではなく「**私たちが当てられませんでした**」です。キッチンにゃんこのように低く出る方がいるので、そこは書き方で担保します。

以前は `spread`（行き先の偏り）を代理指標として3段階に言い分けていましたが、**実測が入ったので置き換えました**。「当たりやすい側です」は読み手に順位を信じてもらう形ですが、「89件試して67%」なら読み手が自分で判断できます。

**確度の低い日を空欄にしません。** 空欄は「その日は出ない」と読まれます。割り振り先が決まらなかった日は「**未定**」と書きます。

**行ごとの営業率は本文に書きません。** 店を選ぶときには予定表の顔ぶれも見ているので、営業率だけを出すと「25%の店になぜ置いたのか」と読めてしまいます。確からしさは枠線と「かも」で伝え、数字は `.maid-plan-rate` として HTML に残します。

**店舗の営業情報だけで人物を実績扱いしません。**人物の記録は `assignment.recorded` とその人の配置記録から取り、`outlook.basis === "actual"` だけでは人物の recorded / settled を真にしません。

| 人物行の区分 | 根拠 |
|---|---|
| 実績 | `actualRoster` に本人の配属記録がある |
| イベント主役の予定 | 公開予定の主役表示と所属店。過去にそこにいた記録ではない |
| 予定・店舗推測 | 公開予定と、店舗集合・配属先の推測 |

以前は店の `state: "open"` や店舗だけの実績を流用し、同じ店に推測で置いた人まで「いた記録があります」と表示していました。また、実績と記念日予定を同じ確定件数に足していました。**表示と注記が同じ判定で揃っていても、根拠の区分が間違っていれば正しくありません。**現在は行のラベルと注記の件数をこの3区分に分け、`tests/store-outlook.js` と `tests/headless-render.js` で検査します。

### 店舗数と店舗の組み合わせは別の予測です

人数から店舗数を見積もることと、開く店の組み合わせを当てることは別です。過去に組み合わせ的中50.9%だった実験はありますが、**50%という理論上限や、店側がいつ決定したかを統計から証明することはできません**。「まだ公表・確認されていない」と「まだ誰も決めていない」も区別します。店舗数・店舗集合・人物配置のどれも、実績のない部分は見込みです。

`sameDayDecisionNote` も、**何店・どの店の両方を公開予定と記録から推測しており、店側の決定時刻や未公開予定は不明**と説明します。「誰も知らない」「当日決まる」「人数なら断定できる」とは主張しません。

### 2番手の店は、予定表の顔ぶれから読みます

上の3つはどれも**実績を必要とします**。ところが記録は 8/30 で止まっており、予定表15日のうち前日が分かるのは1日だけです。残りは曜日傾向しか無く、2・3・4号店がどれも2割前後で並んで意味をなしていませんでした。

**その日の予定表に、各店を本拠とする人が何人載っているか**は実績なしに分かります。これが効きます。

| その店の配属者 | 0人 | 1人 | 2人 | 3人 | 4人 |
|---|---|---|---|---|---|
| 2号店が開く | 27% | 28% | 31% | 45% | 54% |
| 3号店が開く | — | 23% | 28% | 28% | 48% |
| **4号店が開く** | 37% | 35% | 33% | 38% | **30%** |

過去測定では2番手の的中が **34.4% → 42.2%**（372シフト、87勝58敗、p=0.020）でした。CSV先頭1/3をwarmupとし、1号店＋相方1店のケースを対象にした旧 `exp_verify_second` の値です。現データの同設計では374件・34.8%→41.4%・93勝68敗。本番のキッチン除外・補正式まで一致する評価ではなく、将来の本番精度とは区別します。

**4号店は、この見方では読めません。** 配属者が0人でも4人でも3割前後で、動く方向すら一定しません。

**キッチンにゃんこは、この数に入れません。** 公式サイトには配属が載っていますが、実測ではその店に入る率がフロアより13.3ポイント低く（62.6% 対 75.9%、n=5対34、並べ替え検定 p=0.025）、どこにでも入っています。実際 `うる`（配属3号店）と `みりん`（配属1号店）は、どちらも実績の最多が4号店です。外すと表が鋭くなります（3号店の振れ幅が21%→54%）。**予定表に出ているキッチンにゃんこを数に入れていないので、画面の顔ぶれを数えると合いません。** その旨をツールチップに書いています。

なお「4号店が読めないのはキッチンが混ざっているからでは」という見立ては**外れ**でした。除いても振れ幅は9%→8%とほぼ変わりません。キッチン5名に4号店配属が一人もいないためです。

ただし**「4号店は読めない店」ではありません。** 読めないのは「空いた1枠を誰が取るか」のほうだけで、**4号店が開くかどうかは他店から読めます**（同時に2号店が開くなら7%、開かないなら38%）。この違いは下の「4店の関係」を参照してください。

**置き換えではなく、平均からのずれ（尤度比）で元の見込みを更新します。** 置き換えると、同日ルールが出した「昼が2号店なら夜の3号店は1%」のような強い手がかりまで捨ててしまいます。この形なら、表が平均どおりの店は動かないので、**4号店がこの見方で読めないことも特別扱いせずそのまま出ます**。同時に、同日ルールや前日ローテーションが出した4号店の見込みは保たれます。開く店の数の見込みも変えず、3店のあいだの配分だけを動かします。店舗の実績と、イベント主役の予定から固定した店には触れません。

### 4店の関係

以下は**過去測定**（commit `b264c98`、2026-03-03〜09-02 の出荷 `actual` 357シフト、店舗だけの追加実績も含む）です。同じシフトで同時に開いた回数と独立なら期待される回数を比較します。2026-09-03までの現在の出荷 `actual` では354件、CSV限定180日窓では353件で、いずれも357件と別の母集団です。

| 組み合わせ | 実際 / 無関係なら | φ係数 |
|---|---|---|
| 1号 × 2号 | 108回 / 108回 | −0.008 |
| 1号 × 3号 | 106回 / 106回 | −0.010 |
| 1号 × 4号 | 114回 / 114回 | −0.002 |
| 2号 × 3号 | 7回 / 34回 | **−0.353** |
| 2号 × 4号 | 9回 / 36回 | **−0.353** |
| 3号 × 4号 | 12回 / 36回 | **−0.307** |

この窓では1号店と他店の相関はほぼ0、2・3・4号店の3組には負の相関がありました。**無相関は完全な独立や因果的な無関係を意味しません。**「2号店と3号店だけが排他」とする説明も、この集計とは合いません。

```
2・3・4号店のうち何店開くか      その1店の内訳
  1店   281回  78.7%            4号店  96回  26.9%
  0店    48回  13.4%            2号店  95回  26.6%
  2店    28回   7.8%            3号店  90回  25.2%
```

つまり **「1号店 ＋ 2/3/4 のうち1店」** が基本形で、その1枠を3店がほぼ均等に分け合っています。だから4号店の営業率は、他店の状況で大きく動きます。

| 1〜3号店のうち開いた店数 | 4号店の営業率 |
|---|---|
| 1店（＝1号店だけ） | **63.3%** |
| 2店 | 10.5% |
| 3店 | 0% |

メイドさん1人ずつには、その日いそうな店舗を小さなチップで表示します。**1人ずつ独立に判定すると、ほぼ毎日開いている1号店に全員が寄ってしまう**ため（`share` の最上位は roster 全員が1号店でした）、その日そのシフトに出る顔ぶれを、**店ごとの標準人数を定員として割り振っています**。定員は `typicalHeadcount` の比で決め、迷いの少ない人から順に席を取ります。絞り込みを変えても割り振りは動きません。

> **`share` と `pickRate` は用途が違います。取り違えると必ず全員1号店になります。**
> `pickRate[s]` は「その店が**開いていた日**に、その人がそこに入った割合」。
> `share[s]` は「その人が出勤する日に、その店にいる確率」で、**営業率で重み付け済み**です。
> 1号店はほぼ毎日開くので、`share` は誰でも1号店が最大になります。**個人がどの店にいそうかを見るときは、かならず `pickRate` を使ってください。** この罠は集計側でも一度踏んでいます（「全員の最多店が1号店」という結果が出たら、まず `share` を使っていないか疑ってください）。

**チップの数字は確率です。断定ではありません。** 「この人はこの店」と決め打ちすると、たまにしか入らない店を必ず取りこぼします。実際、決定的に割り当てていたときは**4号店にいた256回のうち103回（40%）を外していました**。`ひかり`（4号店の pickRate 0.09）や `ひなり`（0.03）は10回・8回とも全部外しています。

しかし実測では**在籍40名全員が4店舗すべてに入った実績があり**、4号店の pickRate もいちばん低い人で0.017と、ゼロではありません。そこで候補店の中で `pickRate` を合計1に正規化し、**どの店も0%にならない**ようにしています。その日の候補店に絞ったときの的中は上位1店で62.1%、**上位2店なら97.2%**です（4店すべてを候補としたときは `accuracy.maidStoreTop1` / `maidStoreTop2` の53.2% / 75.0%）。

**較正は真ん中では良いのですが、端は当てになりません。** 「40〜49%」と出したときの実測は44.7%ですが、**「90%以上」と出したときの実測は75.6%**です。

| 出した確率 | 件数 | 実測 |
|---|---|---|
| 0〜9% | 241 | **21.2%** |
| 10〜19% | 594 | 20.4% |
| 20〜29% | 974 | 24.8% |
| 30〜39% | 1371 | 31.7% |
| 40〜49% | 1634 | 44.7% |
| 50〜59% | 1543 | 57.6% |
| 60〜69% | 1118 | 67.8% |
| 70〜79% | 674 | 72.1% |
| 80〜89% | 385 | 74.0% |
| 90%以上 | 160 | **75.6%** |

20〜79% の範囲は5ポイント以内で収まりますが、**両端では自信が過剰**です。「6%」と出した店に実際は2割の割合で入っていますし、「94%」と出しても4回に1回は外します。上位2店を併記しているのはこのためで、**いちばん高い数字だけを鵜呑みにしない**でください。

この表は `accuracy.calibration` に入っています。**`tools/data/shifts.csv` だけで計算できる**ので、集計期間や重みを変えて再生成すれば追従します（訓練に直近120日を使い、その先の期間を評価する形で遡って測っています）。README の他の的中率と違い、**この数字はリポジトリの中で検算できます**。

**ただし測っているのは「2店舗以上開いた日」だけです**（`scope: "twoOrMoreOpen"`）。1店舗しか開かない日は、その人がその店にいるのが定義上100%になり、表を不当に良く見せるためです。**候補店が1つでチップが100%と出るときの不確かさは「店舗予測が当たるか」であって、この表の数字ではありません。** 実測では1店舗と見込んだシフト137件のうち、その人が予測した店にいたのは87.2%でした（2店舗のときは72.5%）。候補が1つに絞れるほど人数が少ない日は「1号店だけ」という明快な形が多く、かえって当たります。

なお公式サイトの配属を事前分布に入れたことで、この較正は少し改善しています（Brier 0.2192 → 0.2170、いちばんのずれ 26.8 → 22.8ポイント。全履歴で測った値）。端の確率を均等側へ2割ほど寄せるとさらに縮みますが、これは「90%と言わなくなる」効果が主で、最適な寄せ幅も集計期間で動くため入れていません。上位2店を併記している以上、数字を歪めるより注記で断るほうが情報が減りません。

狭い月グリッドでは最有力の店だけを出し、モバイル幅とツールチップには**候補店すべての確率**を並べます。並び順は割り振り結果（店ごとのまとまり）に合わせているので、チップの先頭はその人が入っているグループの店です。ツールチップには**公式サイトの配属**も添えます。確率は実績が主で配属は弱い事前分布なので、記録が積み上がった人ほど表示は配属から離れます。そのずれを読み手が確かめられるようにするためです。

**上の較正はツールチップにも出しています。** 表示した確率が実測と10ポイント以上ずれる帯（両端）に落ちたときだけ、「90%以上と出したときに実際に当たったのは76%です（開いた店が分かっている日で測った値なので、開く店の予測を外すぶんは含みません）」のように断ります。真ん中の帯では何も足しません。帯の境目は `accuracy.calibration` から計算しているので、再生成すれば追従します。標本が100件に満たないバケットは実測値自体が揺れるため、注記の根拠にしません。

**候補店が1つのシフトでは、この数字を引きません。** `scope` が `twoOrMoreOpen` なので、測っていない領域だからです。代わりに「この夜は1号店だけが開く見込みなので、その見込みが当たればこの店です」と、100%の出どころを構造で説明します。裸の100%を見せないためで、かつ不確かさの在り処（店舗予測が当たるか）を正しく指しています。`scope` を別の値に変えたり `minOpenStores` を足したりすれば、`app.js` を触らずに判定が変わります。

**生誕祭・周年・卒業の主役は、イベントの予定として扱います。**通常の確率による割り振りとは別に所属店へ固定しますが、**その日に実際にそこにいた記録とは区別**します。所属店は `data/schedule.js` の `homeStore`、未登録なら実績に基づく `home` からの推定を使います。この処理を、本人や店側の未公開予定を知っている証拠にはしません。

公式の配属と実績からの推定は**別物**である点に注意してください。在籍40名のうち5名（`える`・`あめる`・`ゆめ`・`うる`・`みりん`）は、配属先と「実際にいちばん入っている店」が食い違います。前者は所属、後者はヘルプを含めた実態です。**うち2名（`うる`・`みりん`）はキッチンにゃんこ**で、配属と関係なく4店を回るためです。

**所属の出どころは2種類あります。** 公式サイトのメイドさん紹介に載っている36名はサイトの配属、まだ載っていない4名（`unpostedMaids`）はお店からの案内です。ツールチップも「公式サイトの配属は2号店」「お店の案内による所属は2号店」と書き分けます。突き合わせられる相手が違うので、同じ顔で出しません。

**お給仕の記録が薄い人は、公式サイトの配属に寄せています。** `pickRate` は「その店が開いていた日のうち、その人がその店にいた割合」ですが、記録が数回しか無い人ではこの割合が当てになりません。そこで公式の配属を**2回の出勤ぶんの重みを持つ事前分布**として混ぜ、記録が増えるほど実績が勝つようにしています（`build-insights.py` の `POSTED_PRIOR`）。

| その人の記録 | n | 事前分布なし | あり | 差 |
| --- | --- | --- | --- | --- |
| 0回（初出） | 145 | 66.2% | **73.1%** | +6.9pt |
| 1〜5回 | 296 | 51.4% | 55.1% | +3.7pt |
| 6〜15回 | 456 | 59.0% | 59.4% | +0.4pt |
| 16〜40回 | 1046 | 70.2% | 70.7% | +0.5pt |
| 41回以上 | 3822 | 66.7% | 66.8% | +0.1pt |
| 全体 | 5765 | 65.9% | 66.5% | +0.6pt（McNemar p=0.037） |

**記録の多い人はほとんど動かず、薄い人だけが大きく上がります。** 41回も出ていれば本人の実績のほうが強い情報なので、これが望ましい形です。一律に下駄を履かせる方式も試しましたが、全体の的中はほぼ同じで、記録の多い人の数字まで動いてしまうため採っていません。重みは0.5〜2.0が有意で、3.0以上は有意になりません。

これがいちばん効くのは、**3か月の見習い期間を終えたばかりの人が `roster` に入ったとき**です。実績がまだ1件も無い状態でも、初日から配属店を出せます。公式サイトに載っていない人（`unlistedMaids`）は従来どおり実績だけで出します。

**キッチンにゃんこは各店1人ずつが基本です。** 実測で1店1人が77.5%（平均1.05人）、キッチン同士の同店率は中央値19%（全ペアの中央値50%に対して）でした。割り振りでは、主役の次に優先して席を決め、すでにキッチンがいる店には減点をかけます。禁止ではありません（実際に13.7%は2人一緒です）。後回しにすると定員が埋まって同じ店に押し込まれてしまうため、順序が重要です。

なお、**この節に書いた精度や根拠はサイトには表示していません。** カレンダーの下に長い解説を出しても冗長なので、バッジと店舗チップのツールチップ（およびスクリーンリーダー向けの読み上げテキスト）に必要なぶんだけ載せ、詳細はこの README に集約しています。

### 予測精度（実測値・正直な注記）

**このサイトの「見込み」は当たりません。** 実測値は次のとおりです。

- 翌日について「2号店と3号店のどちらが開くか」は、昼夜をまとめて **51.4%**（当てずっぽうは 38.3%）
- **昼夜まで分けると 2・3号店は昼 38.3% / 夜 43.0%** で、当てずっぽうと変わりません
- 4号店の翌日は昼 63.6% / 夜 70.1% で、こちらは多少あてになります
- **2日以上先はベースライン並み**です。曜日ごとの平均を出しているだけで、その日の予想には使えません
- メイドさんの店舗を1店に絞って当たるのは、開いている店舗が分かっていれば 65.6%、分からなければ 53.2%（「常に1号店」の 54.2% と同等）。**候補を2店舗まで広げると 75.0%**
- 生誕祭・周年・卒業の日は主役のメイドさんが顔ぶれを選べるため、傾向の計算から除いています

ローテーション表は2種類あります。チップの数値には**シフト別**の `rotation.nextDay` を使い、日単位の `rotation.nextDayByDay` は「その日どちらの店が開くか」という補足にだけ使っています。日単位の表をシフト別の予測に流用すると昼は 38.3%→43.9% と改善しますが夜は 43.0%→33.6% と悪化し、合計ではほぼ同等（n=107）だったため、シフト別のままにしています。

### 何店舗開くかは人数から決めています

開く店舗の数は日によって違います。以下の人数方式の比較値は、境界を導入した当時の測定記録です。**現在の出荷閾値は昼夜とも `[5,12]`**で、現データによる固定閾値比較は[上の節](#開く店の数が表の上限に当たったらそう断ります)にあります。

**ローテーションの確率からは、この店舗数を当てられませんでした。** 1号店の営業率が高すぎて、確率を足しても閾値で切ってもほぼ常に「2店舗」になり、実際にある3店舗の日も1店舗の日も出せません（実測で的中 24〜34%）。

代わりに、**その日カレンダーに出る人数**から決めています。実測では開いた店舗数ごとの人数がはっきり分かれます。

| 開店店舗数 | 昼の人数 | 夜の人数 |
|---|---|---|
| 1店舗 | 4.32人 | 4.26人 |
| 2店舗 | 9.06人 | 8.47人 |
| 3店舗 | 13.33人 | 12.75人 |

`typicalHeadcount` の累積がその日の人数に届くまで店舗を足す、という方式で**昼84.4% / 夜91.8%**の的中でした。ただし**1号店の昼が6.1人あるため、6人が1店舗と判定されてしまう**問題がありました。実測では6人は昼61% / 夜73%で2店舗が多数派です。

係数を掛けたり `p25` を使ったりすると6人は直りますが、上の境界が崩れて12人が3店舗になり、全体の的中が77%に落ちました。そこで**人数ごとの多数決を実測して境界そのものを持たせています**（`openCountByHeadcount`）。

| 人数 | 昼 | 夜 |
|---|---|---|
| 〜5人 | 1店舗 | 1店舗 |
| 6〜 | 2店舗 | 2店舗 |
| 13人〜 | 3店舗 | 3店舗 |

この表は現在の出荷値です。旧境界導入時の的中**昼88.9% / 夜93.2%**とは、人数定義・窓・データ時点を区別してください。`typicalHeadcount` は見習い等も含む実績人数なので、掲載対象proxy人数とは母集団が違います。

なお2店舗に割れるときの人数配分は `typicalHeadcount` の比で決めています。**4号店は4人態勢**なので、6人のシフトなら「1号店4人 + 4号店2人」という実測最多の形になります。

以前ここで見習い人数と説明していた値は、**未掲載者の店舗枠平均**でした。現在の店舗別数値は[店舗ごとの未掲載率](#店舗ごとの未掲載率)で示し、見習いの集計とは分けて検査します。

### どの店が開くかは顔ぶれの配属先から決めています

何店舗開くかが決まったら、次は**どの店か**です。以前は曜日別の営業率の高い順に選んでいましたが、いまは**その日出るメイドさんの配属先**を見ています。「この日この人たちが出るなら、この号店が開く」という見方です。

顔ぶれのうち2号店配属の人が平年（`homeStaffShare`）より多ければ2号店の順位を上げ、少なければ下げます。**店舗の組み合わせを丸ごと当てる的中は 42.9% → 47.7%** になりました（n=709、McNemar p<0.05）。

たとえば9月10日の昼は、出勤9名のうち**2号店配属が1人もいません**（4号店3名・1号店3名・3号店3名）。営業率だけで並べると2号店を選びますが、顔ぶれを見れば4号店です。

**人数ではなく割合で見ています。** 予定表の提出が揃っていない時期でも比が変わらないためです。顔ぶれを伏せた条件でも改善が続きます。

| 方式 | 欠けなし | 15%欠け | 30%欠け |
|---|---|---|---|
| 曜日別の営業率だけ（以前） | 42.9% | 41.5% | 36.0% |
| その日の人数も使う | 47.2% | +2.8（10/10） | **+0.0（5/10）** |
| 誰が出るかを学習して使う | 49.5% | +3.7（10/10） | **+0.5（6/10）** |
| **配属先の割合を使う（現行）** | **47.7%** | **+3.5（10/10）** | **+2.5（10/10）** |

括弧内は、間引く人をランダムに選ぶ乱数の種を10通り変えたときに**改善した回数**です。欠け条件の数値は種によって数ポイント動くので、1回の測定では判断できません。

「誰が出るか」を学習した係数のほうが、予定表が揃っていれば最良（49.5%）です。ただし**3割欠けると当たり外れが半々になり**（10回中6回しか改善しない）、頼れなくなります。配属先の割合を使う方式だけが10回とも改善しました。公式サイトから読める情報だけで済み、説明もしやすいところも利点です。

移行が終わって予定表が揃ったら、学習係数版（49.5%）への切り替えを再検討する価値があります。

#### 選ぶときと出すときで、同じ数字を使います

この顔ぶれの傾き（`applyPostedTilt`）は、**画面に出す割合そのものを動かします**。以前は `expectedOpenStores` が順位づけのときだけ内部で足していて、表示される割合には入っていませんでした。結果として

```
2026-09-09 昼  選ばれた店 1号98% + 3号37%   空いている店 4号40%
2026-09-12 夜  選ばれた店 1号90% + 4号26%   空いている店 2号26% / 3号26%
```

のように、**高いほうが空で、低いほうに顔ぶれがいる**表示が28シフト中5件出ていました。読み手には理由が見えません。

順位と表示の不一致は表示側で直しました。旧実験の521件・当たり店1.32→1.36という値は「過去1年」の固定窓ではありません。CSV先頭1/3をwarmup、曜日標本8件以上で絞り、出荷済み `secondStoreByHome` と**正解の店舗数k**を使う `exp_rank_order` の値です。現データの同設計は525件・1.33→1.38で、本番 `postedTilt` の式とも異なり、将来予測精度としては使いません。

いまは対数オッズで傾けた値をそのまま表示し、`expectedOpenStores` はその割合を上から採るだけです。傾け方を順位づけと同じ式にしてあるので、**選ばれる店は1件も変わらず**（30シフトで差分0）、食い違いだけが5件→0件になりました。テストでは「選ばれなかった店の割合が、選ばれた店の最小を上回らないこと」を全店ぶん見ています。

### 何人態勢の店か

店の規模も違います。`headcountProfile` に最頻値・中央値・四分位・分布を持たせ、店舗チップのツールチップと凡例で使っています。

| 店舗 | 昼 | 夜 |
|---|---|---|
| 1号店 | 6人（36%）・5〜7人が中心 | 6人（44%）・5〜6人 |
| 2号店 | 5人（33%）・5〜7人 | 6人（44%）・6〜7人 |
| 3号店 | 6人（38%）・5〜7人 | 6人（52%）・6〜7人 |
| **4号店** | **4人（58%）・4〜5人** | **4人（61%）・4〜5人** |

**4号店だけ2人少ない体制で固定**されています。1号店の最大13人は生誕祭・周年などのイベント日の外れ値です。

なお、店舗数の判定に使う定員は最頻値ではなく**平均**（`typicalHeadcount`）です。実測で比較したところ平均がいちばん当たりました（昼86.4% / 夜87.5%。中央値は昼86.4% / 夜83.5%、最頻値は昼84.1% / 夜83.5%）。ただし店舗数そのものは、上に書いた `openCountByHeadcount` の実測境界で決めています。`typicalHeadcount` は店舗が決まったあとの人数配分に使います。

また、営業の仕方にも偏りがあります。2〜4号店は片方のシフトだけ開ける日が多数派で（4号店は 84.3%）、昼と夜で開店店舗が違う日が 73% あります。同じ日の中で2号店と3号店が入れ替わった例は 0 件で、入れ替わるのは翌日です（**同日ルールを2・3号店に限っているのはこの実績が根拠です**。ただし「避け合う」こと自体は4号店も同じで、上の「4店の関係」を参照してください）。

**1号店も毎日開いているわけではありません。** 昼は 98.1%、夜は 93.9%（土曜の夜は 90.4%）で、直近180日では夜だけ休みだった日が9日ありました。直近1年では終日休みが2日です。「1号店に行けば必ず開いている」とは考えないでください。

### データの出どころ

[`data/store-insights.js`](data/store-insights.js) は、公式X [@akibazettai](https://x.com/akibazettai) の「ひるにゃんこ / よるにゃんこ」投稿を Wayback Machine 経由で復元した出勤実績から作っています。カレンダーに持たせている実績は直近180日ぶんです。

**集計期間は用途で分けています。**

| 対象 | 期間 | 理由 |
|---|---|---|
| 店舗の営業率・規模・ローテーション・精度 | 直近1年（361日） | 在籍者と無関係なので、長いほうが当たる |
| **メイド個人の店舗傾向** | **直近120日** | 見習いの研修期間が約3か月。1年で集計すると「当時は見習いだった人」を今の在籍として数えてしまう |

期間は `sampleWindow` と `tendencyWindow` に入っています。個人の傾向だけ期間が短いことは、メイドさんのチップのツールチップにも「直近120日」と明記しています。

**店舗側の窓を縮める案は測って却下しました。**「365日は長すぎるのでは、120日では」という問いへの答えです。

| 窓 | 配属から | 実績の傾向から |
|---|---|---|
| 90日 | 42.4% | 43.6% |
| 120日 | 45.8% | 46.6% |
| 180日 | 50.0% | 49.2% |
| **365日** | **50.4%** | **52.5%** |

**短くする理由がありません。**個人の傾向を120日にしているのは在籍が入れ替わるからで、店舗の営業パターンにはその事情がありません。

**READMEの全ての過去実験を再実行できるわけではありません。**今回の閾値・同日補正・移動補正・見習い配置の比較は[評価スクリプト](#評価の再現と限界)で再現できます。それ以外の旧実験値は当時の記録として区別してください。長い窓を改めて比較する場合、直近の [`tools/data/shifts.csv`](tools/data/shifts.csv) と、過去の [`tools/data/shifts-archive.csv.zip`](tools/data/shifts-archive.csv.zip) を合わせられます。

```powershell

```

2019-04-14 から現在まで、34,457行になります。日付は重なりも欠けもありません。

**この記録はもう取り直せません。** X のタイムラインは新人告知100件の固定セットしか返さず、お給仕投稿を含みません。Wayback Machine にも日々の投稿は残りません。`cdn.syndication.twimg.com/tweet-result` は ID が分かれば1件ずつ読めますが、その ID の一覧を作る手段がありません。**消さないでください。**

**投稿の本文は入れていません。** お店の書いたものなので、複製せずに参照できるようにしています。`tweet_id` 列に 6,982件すべての ID が残っているので、本文が要るときはそこから取ってください。

#### 店舗だけ分かっている日を足す

`shifts.csv` は公式Xの「ひる/よるにゃんこ」投稿から復元したもので、**誰が出たか**まで分かります。一方、メイドさん個人の当日投稿などから「この日この店が開いていた」とだけ分かることがあります。その場合は `tools/data/openings.csv` に1行足して再生成します。

```csv
"date","shift","stores","source"
"2026-09-02","昼","s1|s2","メイドさんの当日お給仕投稿"
```

人数が分からないため**統計には混ぜません**（母数がずれます）。`shifts.csv` に記録のあるシフトは上書きしません。この経路で入った日は `actualWithoutRoster` にも記録され、カレンダーのツールチップで「営業した店舗だけが分かっていて、誰がいたかの記録はありません」と断ります。表示される顔ぶれは予定表からの割り振りです。

#### 見習いにゃんこの見分け方

**お店は、見習いを終えたメイドさんに X のアカウントを渡します。**そこを線にしています。

| 条件 | 扱い |
|---|---|
| アカウントがある（卒業表記なし・本人の初日より後に作成） | 昇格済み |
| アカウントが無く、初日から `TRAINEE_MAX_DAYS`（90日）以内 | 見習い |
| アカウントが無いまま初日から90日を過ぎた | この見習い定義から除く。離職が確定したという意味ではない |
| 評価するシフトの日付が直近 `TRAINEE_WINDOW_DAYS`（120日）より前 | **判定しない** |

初日は `debuts.csv` の告知を優先し、無ければ記録上の初出で代用します。

窓を切っているのは、遡るほど**卒業したメイドさんが見習いに見えてくる**ためです。卒業した方も現行のアカウントを持たないので、記録だけでは新人と区別が付きません。窓の外では `actualRoster` に `trainees` キーを置かないので、「判定していない日」と「全員が昇格済みの日」を取り違えずに済みます。

アカウントの有無だけでは足りません。**同じ名前で、卒業した方のアカウントが残っていることがあります。**`ひじり` がそれで、`hijiri_zettai` は2019年作成・プロフィールに卒業表記があり、いまのひじりさんの初日は2026-08-03です。`accounts.csv` の `source` が `卒業済み` のもの、および本人の初日より前に作られたものは、昇格の証拠として数えません。

#### 予測と実績の突き合わせ

実績が届いた日について、**届く前に出していた予測**を [`tools/data/forecast-log.csv`](tools/data/forecast-log.csv) に残しています。カレンダーはこれを読みません。当たり外れを画面に出すためではなく、あとで精度を measure し直すための記録です。

```csv
"date","shift","captured_at","predicted_stores","actual_stores","maid","predicted_store","actual_store","verdict"

`verdict` は `hit` / `miss` / `absent`（予定表にいたが投稿に無い）/ `unlisted`（予定表に無いが出ていた）です。**予定表に載っていなかった人は外れに数えません。**予定表に出ないのはお給仕予定を出していない人で、当てられなくて当然だからです。

### README の数字が、出荷している値と合っているか

python tools/check-readme.py
```

以前の保守で、書いてある数字と実際の食い違いを5回見つけました。以下は**変更経緯の記録**で、現在値の一覧ではありません。

### 在籍・新人の判定について

本番の店舗候補生成後に、真の見習いの存在で絞らず `expectedTrainees > 0` の表示条件だけで比べると、186シフト（**実際は見習いゼロの91件を含む**）で次の結果でした。

### 評価の再現と限界

依存追加なしのPython標準ライブラリとNode.jsで実行します。旧sessionや他worktreeへの固定パスは不要で、GUIは起動しません。Windows子プロセスは `CREATE_NO_WINDOW` と `SW_HIDE` を指定します。

```powershell
py -B -X utf8 tools\evaluate-insights.py --runtime --node node --output tests\fixtures\insights-evaluation.json
py -B -X utf8 tests\test-insights-tools.py
```

Node.jsがPATHにない場合は `--node` に実行ファイルを指定できます。`--runtime` なしは閾値・集計・120日oracle移動対照のみです。結果ファイルは入力・コードのSHA256、条件、分母、正解数、対比較を持ちます。現在の全履歴787件、時間分離snapshot395件を生成して本番関数で比較します。snapshotはメモリ内だけに作り、`--output` で指定した**このcheckout内の結果JSONだけ**を書きます。生成JSや `index.html` は変更しません。

**保存した評価JSONは、明記された入力のsnapshotであり、live CSVに旧件数を強制する期待値ではありません。**標準テストは、合成ケースの既知の正解と、現在入力の集合・式・集計単位の整合を検査します。CSV等を更新したら、通常の `build-insights.py` で出荷JSを再生成し、READMEの現在値の主張を確認・更新し、上の評価コマンドでJSONと入力fingerprintを更新してください。hashはCRLFをLFへ正規化し、出荷JSの `generatedAt` を除きます。過去測定の値は、その時点の記録として現在値とは区別します。

本番 `build()` のうち、予測計算で使わない表示用 `maid_accuracy` / calibration だけsnapshot生成時に省略します。開店・人数・傾向・移動の表はその時点までのデータで毎回再生成し、**openingsも時間filter**します。ただし現在の名簿、配属、アカウント、告知等は固定です。当時の予定提出・欠勤まで復元した完全な事前評価ではありません。報告のp値は単純な対比較で、日間相関や方式選択の影響を除いた将来保証ではありません。

## 公開HTTPからの自動収集

`tools\collect-shifts.py` は、Yahoo!リアルタイム検索の**「アキバ絶対領域」「ひるにゃんこ」各1ページ**から公式status URLを発見し、既存の公開個別表示エンドポイントで作者ID・screen_name・投稿ID・日時・お給仕の書式を確認します。APIキー、課金、ログインCookie、ブラウザー、追加パッケージは不要です。本文全文は保存せず、出典と抽出した事実だけを残します。

```powershell
# 1回だけ。朝5時区切りのJST営業日で直近2日、個別取得は最大20件。
py -B -X utf8 tools\collect-shifts.py --days 2 --max-posts 20
# 観測は保存せず確認（通信制限stateはdry-runでも保存）。
py -B -X utf8 tools\collect-shifts.py --days 2 --max-posts 20 --dry-run --report collector-report.json
# 明示した期間
py -B -X utf8 tools\collect-shifts.py --date-from 2026-09-04 --date-to 2026-09-05
```

**検索インデックスであり、公式timelineの完全な取得ではありません。**候補0件・新規追加0件でも、その日の投稿が無い証拠にはしません。たとえば9月6日午前3時台の既定2日は9月4〜5日で、9月6日の営業や投稿数は未確認です。別作者・引用先のmetadataを公式の投稿本人と取り違えず、解析不能や不一致は失敗理由として残します。403/429などのアクセス制限には従い、無制限retryやproxyによる回避はしません。

### 自動観測と手動実績は別です

単発実行の保存先は **`data\observed-shifts.json`** です。snapshotをatomicに置換し、同じIDの二重追加や重複runを排他lockで防ぎます。**最近2日は新規取得の範囲であり、保存済みの過去日を削る期限ではありません。**0件や部分失敗でも既存の観測を残します。失敗・件数上限で未処理になった候補を成功したcursorだけで飛ばさず、範囲外に持ち越した未処理も失敗・保留のまま報告します。再処理する場合は日付範囲を広げます。

403/429では同じhostへの残りのキーワード・ID要求をそのrunでは止めます。`Retry-After` は観測とは別の `*.http-state.json` に即時保存し、プロセスを再起動した後も指定時刻前にはそのhostへアクセスしません。**dry-runも実通信するため、通信制限stateと排他lockは書きます。**観測のsnapshot・保留・人物の事実はdry-runで変更しません。制限stateを保存できない場合はHTTP要求を始めません。

作者・日時を検証したうえで非給仕と判定したIDは、`resolved` に記録します。公開用コピーへの反映に失敗しても、古いコピーに残った保留が再び未処理として戻らないようにするためです。投稿本文はこの解決記録にも入れません。

このsnapshotは **`shifts.csv` / `STORE_INSIGHTS` / 翌日ローテーションの学習に入力しません**。検索にまだ出ていない店を、統計上の休業・0人という正解にしないためです。手動で確認・補正した人物名簿があるシフトはそちらを優先します。自動化から新しい名前の同一視や手動補正の上書きはしません。

日付の詳細は**店舗名と名前だけのチップ**を中心に表示し、確認できた顔ぶれと**「予定（未確認）」**を分けます。「投稿あり」「投稿実績」「出典」や長い確認見出しを繰り返しません。元の投稿・投稿時刻などは、閉じた**「更新情報」**へまとめています。自動観測がない店は未確認であり、休業ではありません。予定表だけの人物を、不在や観測済みの店にいた証拠として扱いません。同じ人物の別店舗の投稿も保持します。人物別一覧でも、その人物の根拠がある行だけが記録になります。

観測があるシフトでは、**未照合の実名がある場合だけ予定枠を出します**。空の予定枠、予測の店舗チップ、説明段落は出しません。🔰は `traineePeriods` の対象日期間に該当する既知名だけに付けます。この期間は既存 `is_trainee`（初日・公表アカウント・90日条件）から生成し、未掲載というだけでは付けません。未知の名前や「つぽみ」のような異表記を新人や別名と決めつけません。

`traineePeriods` は表示用の期間情報で、自動観測を学習した値ではありません。現在の公表アカウント情報を使う既存判定をそのまま使い、過去の完全な昇格履歴を復元するものでもありません。昇格・初日の根拠を更新した場合は、既存の `tools\build-insights.py` で再生成します。期間外・根拠なしの名前には印を付けません。

ブラウザーは同じサイトの `observed-shifts.json` を `cache: "no-store"` で読むだけです。表示中は1分おきにこのJSONを再読込し、詳細popupを開いている間は自動更新を待ちます。「取得結果を再読込」でも更新できます。既に読込中の応答がpopupへ到着した場合も、選択日・「更新情報」の展開・focus・scrollを保持します。ブラウザーからYahooやXの検索を実行したり、統計を学習したりしません。アプリ・CSSなどの既存刻印は従来どおり更新します。

### GitHub Actionsから収集・公開する構成

本番の継続更新は、標準のGitHub-hosted runnerで**収集→状態保存→検証→frontend限定staging→同じworkflowでPages公開**する構成です。X用APIキーやCookieは使いません。GitHubへの状態保存には、そのrunの既存`GITHUB_TOKEN`を使います。tokenを公開HTTPへ送ったり、stateやartifactへ保存したりしません。

```powershell
# 実runnerの公開HTTP経路を空snapshotから1回確認（観測1件以上の個別検証が必須）
gh workflow run deploy-pages.yml --ref main -f mode=probe
# 最新の公開コードで収集・保存・検証・公開
gh workflow run deploy-pages.yml --ref main -f mode=collect
# 取得はせず、最新の保存済み観測と現在のmainで公開
gh workflow run deploy-pages.yml --ref main -f mode=deploy
```

移行時はprobeと手動`collect`の実成功を確認し、ローカル定期taskを無効化してから毎時00分のcronを有効にします。cronはUTCの毎時00分で、日本時間でも分は00分です。GitHub側の混雑などで開始が遅れる場合があり、厳密な時刻の保証はありません。移行後はPCの起動・ログインに依存しません。

コード公開と収集公開は同じPages concurrency groupで直列化します。production runは実行開始時の**最新main**をcheckoutし、コードpush時にもstate branchの最新観測を復元します。古いcollector runが古いUIやmain同梱の古い観測へ巻き戻すことを避けます。`GITHUB_TOKEN`のpushで別workflowが起動することには依存しません。

`collector-state` branchは**data専用**です。観測snapshot、pending、resolved、通信制限sidecar、恒久の`state-owner.json`、収集中の`lease.json`だけを保存し、そのbranchのコードを実行しません。main/default/code branchの誤指定、所有marker欠落、予期しないファイル、non-fast-forwardを拒否します。force pushはしません。

HTTPの前にleaseをremoteへ保存します。収集後、成功・部分失敗・取得不能のどれでも保存できた事実と通信制限を永続化し、同じcommitでleaseを消します。remote保存が失敗した場合はleaseを残し、次runはHTTPを始めず停止します。部分失敗でも有効な保存済み観測を配信できますが、**Pages構築成功と収集完全成功は別**です。`collectionStatus` / `collectionCode`とUIの更新状態で区別します。

#### 保存失敗時の回復

1. `gh workflow disable deploy-pages.yml` で繰り返し起動を止め、失敗runのログと`collector-recovery-<run-id>` artifactを確認します。このrecovery artifactはPagesには入りません。
2. そのrunのcanonical JSONとHTTP-state JSONを取得し、JSONの形式・作者/日時・pending/resolved・`Retry-After`を確認します。失敗後に別のrunを空stateで始めて制限を無視しないでください。
3. `collector-state`だけの作業コピーで最新remoteを取得し、`state-owner.json`が同じ管理情報であること、leaseが失敗runのものであることを照合します。data branchのスクリプトは実行しません。
4. 検査した2つのstate JSONを復元し、所有markerを維持したまま該当leaseだけを削除して、通常のcommit/pushを行います。競合したら取り直して照合し、forceしません。
5. `gh workflow enable deploy-pages.yml` 後に`mode=collect`で再開します。保存されたcooldownは維持され、期限前はHTTPを保留します。

### Pagesへ載せるファイル

`tools\pages.py stage` は新しい`_site`に、index/app/styles、公開用data、イベントSVGと`version.json`だけを構築します。観測JSONはwhitelist projectionにし、内部pending/resolved/cooldown・ローカルpath・SID・PID・config・log・lock・全文postをfrontendへ持ち込みません。backend、tests、`.git`、README等もPages artifactから除外します。

`version.json`は公開コードのSHA、観測の確認時刻、各公開資産のraw SHA256を持ちます。`index.html`の改行正規化済みcache刻印とは用途が違い、配信物そのものの照合に使います。GitHub Pagesのリポジトリsubpathで動くよう、JSON・画像・scriptは相対参照のままです。

### Windowsのローカル収集（開発・復旧用）

Windows taskは残せますが、本番をActionsへ切り替えた後は無効化し、cloudとの二重定期実行をしません。ローカルだけで使う場合の操作は、非昇格PowerShellから次のとおりです。

```powershell
.\tools\setup-collector-schedule.ps1 -Action Plan
.\tools\setup-collector-schedule.ps1 -Action Install -Cadence Hourly
.\tools\setup-collector-schedule.ps1 -Action Status
.\tools\setup-collector-schedule.ps1 -Action Run
.\tools\setup-collector-schedule.ps1 -Action Stop
.\tools\setup-collector-schedule.ps1 -Action Uninstall
```

Task Schedulerに現在ユーザーの非昇格・パスワード保存なしのタスクを1つ登録します。Actionはconsole-lessな**pythonw.exe**と専用ランチャーで、ブラウザーやコンソールウィンドウを開きません。同時実行はIgnoreNew、開始できなかった場合はStartWhenAvailable、実行時間には上限を設け、PCのwakeは要求しません。**PCの起動・ユーザーのログイン・ネット接続が必要**です。

登録時の設定・観測・ログはユーザー専用 `%LOCALAPPDATA%\AkibazettaiScheduleCollector\` 配下に置きます。永続snapshotを正とし、`--publish` でこのworktreeの `data\observed-shifts.json` へatomicな公開用コピーを作ります。両方をlockし、既存の観測を移行・併合します。コピーに失敗した場合も永続snapshotは失わず、終了codeとレポートに公開失敗を残します。

`Status` で正確なtask名・Action・次回実行時刻・最終結果・データとログの場所を確認できます。`Run` は登録した実タスクを1回だけ手動起動し、`Stop` はそのタスクの現在の実行だけを止めます。`Uninstall` は登録を解除し、観測とログは残します。無関係な既存taskや設定は上書きしません。worktreeやスクリプトを移動した場合は、新しいworktreeから `-Action Install -Cadence Hourly -RepoRoot <新しい絶対パス>` で再登録してください。

別途の常駐が必要な開発用には `collect-shifts.py --watch --interval 3600` もありますが、登録タスクやcloud定期実行との併用はしません。これは実行完了からの間隔であり、毎時00分への整列ではありません。

ローカルcollector単体はAppDataとローカルmirrorまでで、GitHubへpushしません。有料runnerや新しいAPI secretは設定しません。HTTP経路や検索側のHTMLが変わった場合は、結果やエラーを確認してから対応します。

回帰は `tools\tests\test_collect_shifts.py`、`tests\observed-shifts.js` と `tests\browser-calendar.js` にあります。ネットワーク部分は最小のoffline fixtureで故障を作り、実ブラウザー側でも部分観測・未照合予定・手動優先・読込失敗時のsnapshot維持を確認します。

## お給仕情報の更新

事前の予定は [`data/schedule.js`](data/schedule.js)、手動実績から生成した統計は `data/store-insights.js`、公開HTTPの部分観測は `data/observed-shifts.json` に分離しています。描画処理は [`app.js`](app.js) にあるため、通常の予定更新で HTML や描画ロジックを変更する必要はありません。

1. `lastUpdated` を更新します。
2. `schedule` の日付に、`昼` と `夜` の配列を追加・編集します。
3. 記念日・生誕の主役には `featured: true` と、読み上げ・ツールチップ用の `eventLabel` を指定します。
4. メイド服を着ないキッチンにゃんこは `kitchenStaff` に入れます。カレンダーとフィルターに 🍳 が付きます。
5. 在籍が入れ替わったら `roster` と `homeStore` の両方を[公式サイトのメイドさん紹介](https://akibazettai.com/staff/)に合わせます。`roster` の並びは公式の掲載順（ひかりさんが先頭、キッチンにゃんこ5名が末尾）、`homeStore` は各メイドの店舗タブ（`shopNum01`〜`04` が `s1`〜`s4`）です。
6. **見習いを終えたばかりの方は、公式サイトに載る前に予定を出しはじめます。** 予定を出すのはノーマル以上だけなので、提出があること自体が昇格の証拠です。その場合は `roster` に足したうえで、`unpostedMaids` に名前を、`promotedAt` に昇格日を書きます。公式サイトに載ったら `homeStore` に配属を足して、`unpostedMaids` から消してください。
6. `node tests/validate-schedule.js` を実行します。
7. `roster` を変更したときは `py tools/build-insights.py` で `data/store-insights.js` を作り直し、`node tests/validate-insights.js` を実行します。

各シフトの並び順は `roster` の公式順と一致させてください（検証スクリプトが確認します）。カレンダーは予測モードで店舗ごとに見出しを付けてまとめ、**店舗順 → 各店の中は公式の掲載順**で並べます。

初期表示月と日付範囲はアクセス時の日本時間から計算し、**当月1日〜末日の全日**を表示します。日付単位のイベント画像と昼夜の詳細を見られ、期間や人物での絞り込みは補助機能として利用できます。

予定が未確認の日はキーを追加しません。フィルターには `roster` の全員が公式順で表示されるため、予定がないメイドも削除しないでください。

絞り込みで誰も残らなかったシフトは `-`、そもそも公開情報を確認できていないシフトは「確認情報なし」と表示します。

### 実績を取り込む

その日が終わったら、お給仕投稿の URL を渡すだけで `shifts.csv` に入ります。

```
python tools/add-shifts.py https://x.com/akibazettai/status/2095077027061899578 ...
python tools/add-shifts.py --dry-run <URL> ...     # 書かずに見るだけ
python tools/add-shifts.py --confirm-name NAME --dry-run <URL> ...
```

正確な文字列 **`あずにゃん` は既定で許可**しているため、`--confirm-name` は不要です。[公開原典](https://x.com/akibazettai/status/1187933451850174465)で実名として確認した文字列の許可で、別表記や現在の人物との同一視ではありません。

その他の未知の名前で、`にゃん`等の語尾が本文と区別できない場合は保守的に拒否します。**原文の名前列に実名としてあることを確認してから** `--confirm-name NAME` を指定してください。繰り返して複数名を指定できます。指定した名前の語尾除外だけを免除し、本文から名前を拾ったり、別名へ改名したりする機能ではありません。

同じ投稿をURLとIDなどの形で同一呼出しに複数回指定しても、**一度解析に成功した投稿は重複追加しません**。取得・解析に失敗した投稿は処理済みにせず、後続の同じIDで再試行できます。`tools/tests/test_add_shifts.py` と `tools/tests/fixtures/shift-posts.json` に、6投稿の顔文字境界、明示した実名、重複と失敗後再試行の回帰を残しています。後着予定の自動実績化や人物名の自動補正はしません。

fixtureは**投稿本文の転載ではなく**、投稿ID・日時・店見出し・日付・店・シフト・名前の事実データです。テスト内で名前列と顔文字を組み立てて境界を再現します。原文は投稿IDから参照します。

**この手動取込は、指定した投稿だけをcurated実績へ入れます。**検索からの自動発見は上のcollectorに分離し、網羅性を保証しない観測として扱います。

| 経路 | 使えるか |
|---|---|
| `syndication.twitter.com` のタイムライン | **不可**。「新人にゃんこ」「お知らせ」だけを100件返す固定の抜粋で、日々のお給仕投稿を含みません |
| Wayback Machine | **不可**。日々の投稿は保存されません（最後の取得は2026-08-24） |
| 公式サイト | **不可**。予定表のページがありません |
| ID の総当たり | **不可**。1ミリ秒あたり420万通り |
| `cdn.syndication.twimg.com/tweet-result?id=` | **可**。ID さえ分かればログイン無しで1件読めます |

取り込んだら `python tools/build-insights.py` を回してください。

**過去の解析測定**は、既存CSVと保存本文の共通ID 1,462投稿が対象でした。名前一致1,444・名前不一致12・解析不能6で、1,444/1,462 = **98.8%** は正しい値です。残り18投稿は**本当の誤記11＋後着みんと1＋解析不能6**で、「残り12件が全部誤記」ではありません。解析成功分だけなら1,444/1,456 = 99.2%。余分ゼロという照合もこの既存CSVとの集合比較に限られ、最初からCSVに入っていない投稿のrecallは測っていません。

解析不能6投稿（1963801470765256773 / 1969598531561537720 / 2030937921361191365 / 2048689879023063129 / 2053422970404737091 / 2072153332651876477）は名前列の直後に空行なしで顔文字が続く形式でした。該当35行は**既にCSVに存在**し、今回のparser修正でCSVに追加しません。名前列末尾の顔文字、実名「あずにゃん」、同一呼出しの重複URLは道具の標準テストで確認します。

**修正後の再検算は、同じ母集団同士で比較しています。**単独行の正確な顔文字 `⊂(´ω´⊂)))` を名前列の終端として扱い、その後の本文を読み込みません。

| 照合対象 | 旧parser：解析成功 / 名前一致 / 解析不能 | 修正後：解析成功 / 名前一致 / 解析不能 |
|---|---:|---:|
| 元測定時のCSVと保存本文の共通1,462投稿 | 1,456 / 1,444 / 6 | 1,462 / 1,450 / 0 |
| 現在の訂正済みCSVと保存本文の共通1,477投稿 | 1,471 / 1,469 / 6 | 1,477 / 1,475 / 0 |

元1,462投稿の不一致12件は、元CSVの誤記11件＋後着みんと1件のままです。現在の1,477投稿で残る相違2件は、後着みんとと「保存原文もな／CSVもなか」です。**parserを直したことと、CSVの訂正・人物同定の判断を混ぜません。**いずれの再検算でもCSVを書き換えていません。

保存された全12,930投稿の新旧比較では、**旧parserが成功した結果の変更は0件**でした。変わった80件はすべて解析不能からの復元で、現在CSV＋archiveの名前集合と80件とも一致しました（6件が現在の対象期間、74件は期間外）。これは保存資料の範囲での検証であり、未収集投稿全体のrecallではありません。

投稿の形はこうなっています。名前は空行に挟まれたひと固まりで並び、記念日の主役には絵文字が付きます。

```
【アキバ絶対領域】
よるにゃんこ🐈🍓
                    <- 空行
あむ
きらり🎉             <- 主役
                    <- 空行
きらりちゃんの周年を…   <- ここから本文
```

**本文と名前列の境界を誤ると、文章まで名前になります。** `巫女コスデー`7行（再投稿を含む6店舗シフト）と `あとから`1行が混入していました。`あとから`削除の出典は投稿 **1958364381546418519** の「あとから、えみるちゃんもくるにゃんね〜」です。投稿 **1966698804696023226** の「みんとちゃん、こいちゃんもあとから来るにゃんね〜」は別件で、実名が存在する後着予定を確定実績に含めるかという仕様問題です。出典を混同しません。

同じ理由で `まこと` と `まこっちゃん` が同じ投稿に両方入っている行が3つありました。投稿に出ているのは `まこと` で、`まこっちゃん` は本文の「まこっちゃん周年」からです。**同じ方なので二重に数えていました。**

この11行の削除は公開原文との照合で妥当と確認されています。まこっちゃん3行の削除後も同じ投稿の `まこと` は残り、ALIAS と一致します。9/3夜の原文「もな」と昼「もなか」は異なり、同一人物という直接の公式訂正は未確認です。`みずれ` / `みひん` も原文どおりで、自動統合は保留します。

## 公開状態

リポジトリは公開（public）で、GitHub Pages でサイトを公開しています。無料プランの GitHub Pages は公開リポジトリでしか使えないため、非公開にすると Pages も停止します。

`main` への push で [ワークフロー](.github/workflows/deploy-pages.yml)が動き、データ検証に成功した場合だけサイトが更新されます。

HTML、CSS、JavaScript、予定データはリポジトリのプロジェクトパスで動作する相対パスを使用しています。

### 更新がブラウザーに届くまで

`index.html` は読み込むファイルに中身のハッシュを付けています（`app.js?v=6c9e3ac864`）。`tools/build-insights.py` が書き込み、`tests/validate-schedule.js` が照合します。手で `app.js` や `styles.css` を直したあと再生成を忘れると、そこで落ちます。

これは**新しい `index.html` が古い `app.js` と組になる**のを防ぐためのものです。付ける前は、データを更新しても画面に予測が出たままになりました。

**`index.html` 自体には付けられません。** GitHub Pages は `Cache-Control: max-age=600` を返すので、**デプロイ後10分は、一度開いたブラウザーに古い `index.html` が出ます**。古い `index.html` は古いハッシュを配るので、資産も古いままです。10分で自然に解消します。

**デプロイ直後に本番を確かめるときは、`index.html` にキャッシュ避けを付けてください。**

```
https://agurakakenai.github.io/akibazettai-schedule-calendar/?fresh=1
```

これを付けずに「反映されていない」と判断した例が、開発中に2回あります（1回は本当にキャッシュ、1回は正しい実装をバグと誤認しかけた）。

### 非公開に戻す場合

1. リポジトリを private にすると、GitHub Pages は自動的に停止します（サイトは 404 になります）。
2. その状態で push すると deploy ジョブが失敗するため、deploy ジョブに `if: github.event_name == 'workflow_dispatch'` を付けて手動実行専用にします。
3. 閲覧は [`preview.cmd`](preview.cmd) でのローカルプレビューに切り替えます。

### 自分だけが見られる形で公開したい場合

| 方法 | リポジトリ | サイト | 費用 |
|---|---|---|---|
| GitHub Pages（無料プラン） | 公開が必須 | 誰でも閲覧可 | 無料 |
| GitHub Pages（Pro） | 非公開にできる | **URL を知っていれば誰でも閲覧可** | 月 $4 |
| Azure Static Web Apps | 非公開のまま | **許可した本人だけ** | 無料枠 |
| Cloudflare Tunnel + Access | 非公開のまま | 許可した本人だけ | 無料（独自ドメインが必要） |

GitHub Pages は Pro にしてもサイト自体は公開されます。サイトを本人だけに限定できるのは GitHub Enterprise Cloud だけです。

[`staticwebapp.config.json`](staticwebapp.config.json) には Azure Static Web Apps 用の設定を用意済みです。全ページを `schedule-reader` ロールに限定し、未認証のアクセスは GitHub ログインへリダイレクト、ロールがないアカウントには [`unauthorized.html`](unauthorized.html) を返します。

#### Azure Static Web Apps で非公開のまま閲覧できるようにする手順

1. [Azure Portal](https://portal.azure.com/) で「静的 Web アプリ」を作成し、プランは **Free** を選びます。
2. デプロイソースに GitHub を選び、このリポジトリと `main` ブランチを指定します。
3. ビルドのプリセットは「カスタム」、アプリの場所は `/`、API の場所は空、出力先は `/` にします（ビルド不要のため）。
4. 作成すると `.github/workflows/azure-static-web-apps-*.yml` が自動で追加され、以降は push でデプロイされます。
5. リソースの **設定 → ロールの管理 → 招待** を開きます。
   - 承認プロバイダー: **GitHub**
   - 招待するユーザー: 自分の GitHub **ユーザー名**（Entra ID を選んだ場合はメールアドレス）
   - ロール: `schedule-reader`
   - 有効期限: 最大 168 時間（7日）
6. 生成された招待リンクを自分で開き、GitHub でサインインします。**リンクを開いて初めてロールが付与されます。**

これで、サイトの URL にアクセスできるのはロールを付与したアカウントだけになります。ロールのないアカウントがサインインしても [`unauthorized.html`](unauthorized.html) が返るだけです。リポジトリは非公開のままで構いません。

補足:

- 事前構成済みのログイン方法は **GitHub と Microsoft Entra ID** で、Free プランでも追加設定なしに使えます。Google などを足す場合は Standard プランが必要です。
- 招待によるロール付与は全プランで使えます。Standard 限定なのは「関数でロールを自動割り当てする」機能だけです。
- Free プランの上限は帯域 100 GB/月・アプリサイズ 250 MB・カスタムドメイン 2 件で、このサイトの規模なら十分です。
- アクセスを取り消したいときは、同じ「ロールの管理」からユーザーを削除します。
